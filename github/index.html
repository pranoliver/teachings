Chapter 2

What is Version Control?

Version control is a system that records changes to a file or set of files over time so you can recall specific versions later. Git is the most popular version control system in the world.

Without vs. With Git

Git keeps a clean timeline of every saved version instead of a mess of duplicate files.

Key terms

Repository (repo)
A folder tracked by Git.
Commit
A snapshot of your files at a point in time.
Branch
An independent line of development.
Remote
A version of your repo hosted on another machine (like GitHub).

Chapter 4

Configuring Git

Before you start saving work, tell Git who you are. This information is attached to every commit you make. 

# Set your name and email (
use the same email as your GitHub account)
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
# Choose your default branch name
git config --global init.defaultBranch main
# Check your settings
git config --list

What does --global mean?

It means the setting applies to all repositories on your computer. You can also use --local inside a specific repo if you need a different identity for work and personal projects.

Try it yourself

Run the three configuration commands above, then verify with git config user.name and git config user.email .

Your First Repository

# Git creates a hidden .
git directory that stores history
ls -la  
# (or dir on Windows)

Chapter 6

Staging & Committing

Git saves changes in two steps: staging (selecting what to save) and committing (taking the snapshot).

The Git workflow 

# Create a file
echo "Hello, Git!" > readme.txt
# Check the status of your repo
git status
# Stage the file (add it to the 
next commit)
git add readme.txt
# Commit the file with a descriptive message
git commit -m "Add initial readme file"
# Stage all changes in the current directory and commit at once
git add .
git commit -m "Describe the changes here"

Writing good commit messages

A commit message should explain why the change exists. Future you (and your teammates) will thank you.

  • Use the present tense: "Add login form" not "Added login form"
  • Keep the first line under 50 characters
  • Add a blank line and more details if needed

Try it yourself

Create a file, stage it, commit it, then run git status again. It should say "nothing to commit, working tree clean".

Chapter 7

Viewing History

Git remembers every commit. You can inspect the past, compare versions, and find exactly when a change was introduced. 

# Show commit history
git log
# Compact one-line history
git log --oneline
# Show what changed in the last commit
git 
show
# See which files changed between commits
git diff HEAD~1 HEAD

What is HEAD ?

HEAD is a pointer to the current commit you're looking at. HEAD~1 means "one commit before the current one". This is useful for comparing recent versions.

Checkpoint

Make two or three commits, then run git log --oneline . Can you read the short history?

Chapter 8

Branching

Branches let you work on separate features or experiments without affecting the main project. Think of them as parallel timelines.

Main branch vs. feature branch

Branches split off to isolate work, then merge back when ready. 

# List branches
git branch
# Create and switch to a new branch
git checkout -b feature/login
# (newer Git versions can 
use: 
git switch -c feature/login)
# Switch back to main
git checkout main
# (or: 
git switch main)
# Rename a branch
git branch -m old-name new-name

Try it yourself

Create a branch named feature/hello , add a file, commit it, then switch back to main . Notice the new file disappears (it's only on the branch).

← Previous Next: Merging →

Chapter 9

Merging

Merging combines the work from one branch into another. Usually you'll merge a feature branch back into main .

A fast-forward merge 

# Switch to the branch that should receive the changes
git checkout main
# Merge the feature branch in
git merge feature/login
# If no conflicts, Git combines the histories automatically

Merge strategies

  • Fast-forward : main hasn't changed since the branch was created, so Git simply moves the pointer forward.
  • Three-way merge : main has new commits too, so Git creates a new merge commit combining both histories.

Checkpoint

Merge your feature/hello branch into main , then run git log --oneline --graph --all to see the history graph.

Chapter 10

Resolving Merge Conflicts

A conflict happens when Git can't automatically combine changes. This is normal and easy to fix once you know what to look for. 

# When a conflict appears, Git marks the file like this:
<<<<<<< HEAD
This is the version on your current branch.
=======
This is the version from the branch you're merging.
>>>>>>> feature/login

How to resolve

  1. Open the conflicting file in your editor.
  2. Search for <<<<<<< markers.
  3. Choose which changes to keep, or combine them manually.
  4. Delete the conflict markers.
  5. Stage the resolved file: git add filename
  6. Finish the merge: git commit

Try it yourself

Create two branches that both edit the same line of the same file. Merge one, then merge the other to trigger a conflict. Resolve it manually and complete the merge.

Chapter 11

GitHub Setup

GitHub is a web platform for hosting Git repositories and collaborating with others. If you don't have an account yet, now is the time.

1. Create an account

Go to github.com and sign up with your email. Use the same email you configured in Git.

Sign up on GitHub →

2. Create a repository

Click the + icon → New repository. Give it a name, optional description, and choose public or private.

Repository settings explained

  • Public : anyone can see your code.
  • Private : only you and invited collaborators can see it.
  • README : a markdown file that describes the project. Check this box.
  • .gitignore : tells Git which files to ignore (e.g., build artifacts, secrets).
  • License : tells others how they can use your code.

Chapter 12

Connecting to GitHub

You can connect to GitHub using HTTPS (password or token) or SSH (cryptographic key pair). SSH is the most convenient once set up.

HTTPS

Easier to start, but GitHub requires a Personal Access Token instead of your password.

Create a token →

SSH

More secure and no token needed after setup. Recommended for regular use.

Setting up SSH 

# Generate an SSH key (
use the email from your GitHub account)
ssh-keygen -t ed25519 -C "you@example.com"
# Start the SSH agent and add the key
 eval "$(
ssh-agent -s)"
ssh-add ~/.
ssh/id_ed25519
# Copy the public key to your clipboard
# macOS:
pbcopy < ~/.
ssh/id_ed25519.pub
# Linux:
cat ~/.
ssh/id_ed25519.pub
# Windows (Git Bash):
clip < ~/.
ssh/id_ed25519.pub
# Then paste it into GitHub → Settings → SSH and GPG keys → New SSH key

Test your connection 

ssh -T 
git@github.com
# Expected: Hi username! You've successfully authenticated...

Checkpoint

Set up SSH and run ssh -T git@github.com . You should see a greeting with your GitHub username.

Chapter 13

Push & Pull

Now we connect your local repo to GitHub. Push sends your commits to GitHub. Pull downloads the latest changes from GitHub.

Local ↔ Remote workflow

Linking and pushing 

# Add a remote named "origin" pointing to your GitHub repo
git remote add origin 
git@github.com:your-username/learning-github.
git
# Verify the remote
git remote -v
# Push your main branch to GitHub
git push -u origin main
# Later, when you have new local commits, just run
git push
# Download the latest changes from GitHub
git pull

Try it yourself

Push your local my-first-repo to GitHub. Then edit the README on GitHub, commit the change, and pull it back to your computer.

Chapter 14

Forking & Cloning

Cloning copies a remote repository to your computer. Forking makes your own copy of someone else's repository on GitHub.

Clone

Use this when you have access to a repo and want to work on it locally. 

git clone 
git@github.com:your-username/learning-github.
git

Fork

Use this when you want to contribute to a repo you don't own. Click "Fork" on GitHub, then clone your fork.

When to fork vs. clone

  • Clone : you are the owner or a direct collaborator.
  • Fork : you want to suggest changes to someone else's project.
  • Fork + clone : the standard workflow for open-source contributions.

Try it yourself

Find a small open-source project on GitHub. Fork it, clone your fork, and open it in your code editor.

Chapter 15

Pull Requests

A Pull Request (PR) is a proposal to merge your branch into another. It lets teammates review, discuss, and approve changes before merging.

Pull Request lifecycle

Opening a PR

  1. Push your branch to GitHub: git push -u origin feature/login
  2. Visit the repository on GitHub.
  3. Click Compare & pull request .
  4. Write a clear title and description.
  5. Request reviewers if working with a team.
  6. Click Create pull request .

Good PR habits

  • Keep PRs small and focused on one thing.
  • Explain why the change is needed, not just what changed.
  • Add screenshots for UI changes.
  • Link related issues with phrases like "Fixes #12".

Try it yourself

Create a branch, make a small change, push it, and open a Pull Request in your own repository. Then merge it.

Chapter 16

Collaboration Workflows

Teams follow workflows to keep the main branch stable and make reviews predictable. Here are the two most common patterns.

Feature branch workflow

Every new feature gets its own branch. When complete, open a PR to merge into main .

Fork & pull workflow

External contributors fork the repo, clone their fork, push branches there, and open PRs against the original repo.

Typical team flow

  1. Pull the latest main : git pull origin main
  2. Create a feature branch: git checkout -b feature/xyz
  3. Commit your work regularly.
  4. Push the branch and open a PR.
  5. After approval, merge into main .
  6. Delete the old branch locally and remotely. 
# Delete a branch after merging
git branch -d feature/login       
# local
git push origin --delete feature/login  
# remote

Chapter 17

Issues, Labels & Milestones

GitHub Issues are lightweight tickets for bugs, ideas, and tasks. Labels and milestones help you organize them.

Issues

Track bugs, feature requests, and discussions. Each issue has a number, title, description, and comments.

Labels

Color-coded tags like bug , enhancement , help wanted . Use them to filter and prioritize.

Milestones

Group issues by deadline or release, e.g., "v1.0" or "October sprint". 

# Link a commit to an issue using a keyword
git commit -m "Fix navigation bug. Closes #7"

Try it yourself

Open your GitHub repo, create an issue titled "Add a welcome section", add the enhancement label, and assign it to yourself.

Chapter 18

GitHub Pages

GitHub Pages lets you host a static website directly from a repository — perfect for portfolios, documentation, and project homepages.

How to enable Pages

  1. Go to your repository on GitHub.
  2. Click Settings → Pages .
  3. Under "Build and deployment", select Deploy from a branch .
  4. Choose main and folder /(root) or /docs .
  5. Save. Your site will be available at https://your-username.github.io/repo-name/ . 
# Example: create a simple homepage
# In your repo root, create index.html and commit it
echo "<h1>Hello, GitHub Pages!</h1>" > index.html
git add index.html
git commit -m "Add GitHub Pages homepage"
git push

Try it yourself

Add an index.html to your repository, enable GitHub Pages, and visit your live site.

Chapter 19

GitHub Actions (CI/CD Basics)

GitHub Actions automates tasks like testing, building, and deploying your code whenever something changes.

Automation trigger → job → result

Example workflow file

Create .github/workflows/demo.yml in your repo: 

name: Demo Workflow
on: [push, pull_request]
jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Say hello
        run: echo "GitHub Actions is running!"

Try it yourself

Add the workflow file above, commit and push, then visit the Actions tab on GitHub to watch it run.

Chapter 20

GitHub Copilot

GitHub Copilot is an AI-powered coding assistant. It suggests code completions, entire functions, and explanations inside your editor.

How to use it

  • Install the Copilot extension in VS Code, JetBrains, or Neovim.
  • Sign in with your GitHub account.
  • Start typing and accept suggestions with Tab .

Good practices

  • Review every suggestion before accepting.
  • Don't paste secrets or private data.
  • Use it to learn, not to skip understanding.

Try it yourself

If you have access to Copilot, open your code editor and type a function comment. See what suggestion appears.

Chapter 21

Security Features

GitHub provides tools to keep your code and dependencies secure.

Dependabot

Automatically scans your dependencies and opens PRs to update vulnerable or outdated packages.

Code scanning

Uses CodeQL to find security vulnerabilities and bugs in your code. Enable it under Security → Code scanning.

Protect sensitive data

  • Never commit passwords, API keys, or private tokens.
  • Use .gitignore for files like .env .
  • Use GitHub Secrets for Actions workflows instead of hardcoding values.
  • Enable two-factor authentication on your GitHub account.

Checkpoint

Check that your GitHub account has two-factor authentication enabled. Visit Settings → Password and authentication.

Chapter 23

Best Practices & Resources

You're almost at the finish line. These habits will help you use Git and GitHub confidently in real projects.

Git habits

  • Commit often with clear messages.
  • Use branches for every new feature or fix.
  • Pull before you push to avoid surprises.
  • Review diffs before committing.

GitHub habits

  • Write helpful README files.
  • Use issues and PRs for communication.
  • Keep main deployable at all times.
  • Protect your main branch with review rules.
