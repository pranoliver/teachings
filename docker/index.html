Chapter 2

What is Docker?

Docker is a platform for developing, shipping, and running applications inside containers. Containers package an application with everything it needs — libraries, dependencies, and configuration — so it runs the same way everywhere.

Containers vs. Virtual Machines

Why containers matter

  • Consistency: The app behaves identically on a laptop, test server, and production cluster.
  • Efficiency: Containers share the host OS kernel, so they start faster and use less memory than VMs.
  • Isolation: Each container has its own filesystem, processes, and network namespace.
  • Portability: Build once, run anywhere Docker is installed.

Chapter 4

Images vs. Containers

An image is a read-only template that defines what runs inside a container. A container is a running instance of an image.

Image

  • Read-only blueprint
  • Contains OS files, app code, libraries, and metadata
  • Stored in layers for efficient reuse
  • Identified by a name and tag, e.g. nginx:alpine

Container

  • Runnable instance of an image
  • Has its own writable layer and isolated process tree
  • Can be started, stopped, paused, and removed
  • Many containers can share the same image
# Pull an image from Docker Hub
docker pull nginx:alpine

# See downloaded images
docker images

# Run a container from an image
docker run --name my-nginx -d -p 8080:80 nginx:alpine

# List running containers
docker ps

# List all containers (including stopped)
docker ps -a

# Stop and remove a container
docker stop my-nginx
docker rm my-nginx

Chapter 5

Your First Container

Let's run an interactive container and inspect it from the outside.

# Run an interactive Alpine Linux shell
# --rm removes the container when you exit
# -it gives you an interactive terminal
docker run --rm -it alpine:latest sh

# Inside the container, try these commands:
uname -a
cat /etc/os-release
ps aux
exit

Common run flags explained

--rm
Delete the container after it exits.
-it
Interactive + TTY, used for shells.
-d
Run detached (in the background).
-p HOST:CONTAINER
Map a host port to a container port.
--name
Give the container a readable name.
-e KEY=VALUE
Set an environment variable.

Checkpoint

Run the Alpine shell, run uname -a, then exit. Verify the container is gone with docker ps -a.

Chapter 6

Running a Linux OS Container

Docker is not a full VM, but it can run a minimal Linux userland. This is useful for testing scripts, debugging environments, or running command-line tools consistently.

# Start a persistent Ubuntu container in the background
docker run -d --name devbox --hostname devbox ubuntu:24.04 sleep infinity

# Execute commands inside the running container
docker exec devbox apt-get update
docker exec devbox apt-get install -y curl vim git

# Open an interactive shell inside it
docker exec -it devbox bash

# Inside the container, inspect the environment
cat /etc/os-release
whoami
hostname

# Stop and clean up when done
docker stop devbox
docker rm devbox

Realistic use case: test a script in isolation

Imagine you need to run a Python script on a fresh Ubuntu machine but do not want to install anything on your laptop.

# Create a script on your host
mkdir -p ~/docker-scripts
cat > ~/docker-scripts/hello.sh <<'EOF'
#!/bin/bash
echo "Running on $(cat /etc/os-release | grep PRETTY_NAME | cut -d'=' -f2)"
EOF

# Run it inside an Ubuntu container, mounting your script folder
docker run --rm -v ~/docker-scripts:/scripts ubuntu:24.04 bash /scripts/hello.sh

Chapter 7

Running PostgreSQL in Docker

Databases are one of the most common services to containerize. Docker makes it trivial to spin up PostgreSQL for local development, testing, or CI pipelines.

# Create a dedicated Docker volume for persistent database storage
docker volume create pgdata

# Run PostgreSQL 16
docker run -d \
  --name postgres \
  -e POSTGRES_USER=admin \
  -e POSTGRES_PASSWORD=secret123 \
  -e POSTGRES_DB=appdb \
  -v pgdata:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:16-alpine

# Check the logs
docker logs postgres

# Connect with psql from inside the container
docker exec -it postgres psql -U admin -d appdb -c "\dt"

# Create a table and insert data
docker exec -it postgres psql -U admin -d appdb -c "
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  email TEXT UNIQUE NOT NULL
);
INSERT INTO users (name, email) VALUES
  ('Alice', 'alice@example.com'),
  ('Bob', 'bob@example.com');
"

# Query the data
docker exec -it postgres psql -U admin -d appdb -c "SELECT * FROM users;"

Why use a named volume?

  • Container storage is ephemeral: deleting the container deletes its data.
  • A named volume lives outside the container and survives restarts.
  • You can back up, migrate, or inspect the volume independently.

Checkpoint

Start PostgreSQL, create the users table, insert a row, and query it. Then stop and restart the container and verify the data is still there.

Chapter 9

Volumes & Networks

Containers are isolated by default. Volumes share data with the host or between containers. Networks let containers talk to each other safely without exposing ports to the host.

Volumes

# Create a volume
docker volume create mydata

# Use it in a container
docker run --rm -v mydata:/data alpine \
  sh -c "echo hello > /data/file.txt"

# Read it from another container
docker run --rm -v mydata:/data alpine \
  cat /data/file.txt

Networks

# Create a bridge network
docker network create mynet

# Run containers on the same network
docker run -d --name db --network mynet \
  -e POSTGRES_PASSWORD=secret postgres:16-alpine

docker run --rm --network mynet alpine \
  sh -c "apk add --no-cache postgresql-client \
  && psql postgres://postgres:secret@db/postgres -c 'SELECT 1;'"

Chapter 10

Writing a Dockerfile

A Dockerfile is a recipe for building a Docker image. It turns your application into a portable artifact.

# Dockerfile for a tiny Python Flask app
FROM python:3.12-slim

# Create a non-root user for security
RUN groupadd -r appgroup && useradd -r -g appgroup appuser

WORKDIR /app

# Install dependencies first for better layer caching
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy application code
COPY . .

# Switch to non-root user
USER appuser

EXPOSE 5000

CMD ["python", "app.py"]
# requirements.txt
flask==3.0.0
# app.py
from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return {"message": "Hello from Docker!"}

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
# Build the image
docker build -t my-flask-app .

# Run it
docker run -d -p 5000:5000 my-flask-app

# Test
curl http://localhost:5000

Key Dockerfile instructions

FROM
Base image to start from.
WORKDIR
Set the working directory.
COPY
Copy files from host to image.
RUN
Execute commands during build.
EXPOSE
Document which ports the container listens on.
CMD
Default command when the container starts.

Chapter 11

Docker Compose

Compose lets you define and run multi-container applications with a single YAML file. It is the standard way to orchestrate local development stacks.

services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/share/nginx/html:ro

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret123
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5432:5432"

volumes:
  pgdata:
# Start all services in detached mode
docker compose up -d

# View running services
docker compose ps

# View logs
docker compose logs -f

# Stop and remove everything
docker compose down

# Stop but keep volumes
docker compose down --volumes

Checkpoint

Create a docker-compose.yml with Nginx and PostgreSQL, run docker compose up -d, then visit localhost:8080 and connect to the database on port 5432.

Chapter 12

Full-Stack App: App + DB + Proxy

This section combines a custom Python API, PostgreSQL, and Nginx into one realistic, runnable stack managed by Docker Compose.

Project layout

docker-demo/
├── docker-compose.yml
├── api/
│   ├── Dockerfile
│   ├── requirements.txt
│   └── app.py
├── nginx/
│   └── default.conf
└── html/
    └── index.html

1. API service

# api/app.py
import os
from flask import Flask, jsonify
import psycopg2

app = Flask(__name__)

DATABASE_URL = os.environ.get(
    "DATABASE_URL",
    "postgres://admin:secret123@db:5432/appdb"
)


def get_db():
    return psycopg2.connect(DATABASE_URL)


@app.route("/health")
def health():
    return jsonify({"status": "ok"})


@app.route("/users")
def users():
    conn = get_db()
    cur = conn.cursor()
    cur.execute("SELECT id, name, email FROM users;")
    rows = cur.fetchall()
    cur.close()
    conn.close()
    return jsonify({"users": [{"id": r[0], "name": r[1], "email": r[2]} for r in rows]})


if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
# api/requirements.txt
flask==3.0.0
psycopg2-binary==2.9.9
# api/Dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

USER nobody
EXPOSE 5000
CMD ["python", "app.py"]

2. Nginx config

server {
    listen 80;
    server_name localhost;

    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://api:5000/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

3. Compose orchestration

services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret123
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U admin -d appdb"]
      interval: 5s
      timeout: 5s
      retries: 5

  api:
    build: ./api
    environment:
      DATABASE_URL: postgres://admin:secret123@db:5432/appdb
    depends_on:
      db:
        condition: service_healthy

  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/share/nginx/html:ro
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - api

volumes:
  pgdata:
-- init.sql
CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT UNIQUE NOT NULL
);

INSERT INTO users (name, email) VALUES
    ('Alice', 'alice@example.com'),
    ('Bob', 'bob@example.com')
ON CONFLICT (email) DO NOTHING;
# Build and start the full stack
docker compose up --build -d

# Test the static frontend
curl http://localhost:8080

# Test the API through Nginx
curl http://localhost:8080/api/health
curl http://localhost:8080/api/users

# Tear everything down
docker compose down --volumes

Checkpoint

Build and run the full-stack demo. Verify the static site on /, the health endpoint on /api/health, and the users endpoint on /api/users.

Chapter 13

Registries & CI/CD

Once an image is built, it is pushed to a registry so other machines can pull and run it. This is the foundation of Docker-based CI/CD pipelines.

# Log in to Docker Hub
docker login

# Tag an image with your Docker Hub username
docker tag my-flask-app username/my-flask-app:1.0.0

# Push it
docker push username/my-flask-app:1.0.0

# Pull and run it anywhere
docker pull username/my-flask-app:1.0.0
docker run -d -p 5000:5000 username/my-flask-app:1.0.0

Typical CI/CD pipeline

# .github/workflows/docker.yml example
name: Build and Push Docker Image
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}
      - uses: docker/build-push-action@v5
        with:
          context: ./api
          push: true
          tags: ${{ secrets.DOCKER_USERNAME }}/my-api:${{ github.sha }}

Chapter 14

Security Best Practices

Containers are not secure by default. A few habits make a dramatic difference in production.

  • Run as non-root: Use USER in Dockerfiles and avoid root whenever possible.
  • Use small base images: Prefer alpine, slim, or distroless over full OS images.
  • Pin image tags: Use specific versions like postgres:16.3-alpine, not latest.
  • Keep secrets out of images: Pass passwords via environment variables or secret mounts, never hard-code them.
  • Scan images: Use docker scout or Trivy to find known vulnerabilities.
  • Read-only filesystem: Add --read-only and only mount writable volumes where needed.
# Scan an image for vulnerabilities
docker scout quickview my-flask-app

# Run a read-only container with a tmpfs for /tmp
docker run --rm --read-only --tmpfs /tmp:rw,noexec,nosuid,size=100m my-flask-app

Chapter 15

Production Considerations

Docker alone is great for single hosts. In production, you usually orchestrate many containers across many machines. The most common tool for that is Kubernetes, but managed services and Docker Swarm are also options.

Scaling options

  • Docker Compose: Best for local development and small single-host deployments.
  • Docker Swarm: Built-in clustering, simpler than Kubernetes, good for medium workloads.
  • Kubernetes: Industry standard for large, resilient, multi-cloud systems.
  • Managed services: AWS ECS, Azure Container Apps, Google Cloud Run, Railway, Fly.io.

Production checklist

  • Use health checks for every service.
  • Centralize logs with structured logging or a log shipper.
  • Monitor resource usage and set memory/CPU limits.
  • Run database backups outside the container lifecycle.
  • Use reverse proxies and TLS termination for public endpoints.
