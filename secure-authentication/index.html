Security Track

Secure Authentication

Authentication and authorization are the front gates of every application. When they fail, attackers walk in as admins, users, or third-party services. This tutorial covers password auth, OAuth 2.0, OpenID Connect, SSO, multi-factor authentication, role-based access control, and how real companies have learned these lessons the hard way.

By the end, you will be able to design and implement a secure identity layer for a Node.js or Python application, integrate social login, enforce fine-grained permissions, and pass a practical security capstone.

Identity, Authentication & Authorization

These three terms are often mixed up but mean different things:

Identity

Who the user is: user ID, email, profile, groups, and organizational context.

Authentication

Proving identity: passwords, tokens, biometrics, OTPs, or identity-provider assertions.

Authorization

What the user may do: roles, permissions, scopes, and access-control policies.

A secure system checks both: authentication first ("are you really Alice?"), then authorization ("is Alice allowed to refund this payment?").

Password-Based Authentication

Passwords are still the most common authentication factor. Their security depends on how they are hashed, how login attempts are limited, and how sessions are issued after a successful login.

Real-world example

In 2012, LinkedIn lost 6.5 million password hashes. They used SHA1 without a salt , allowing attackers to crack millions of passwords within hours using rainbow tables. LinkedIn later revealed the total was closer to 167 million accounts.

Unsafe password storage 

# ❌ VULNERABLE: SHA1 without salt
import hashlib
def store_password(password: str) -> str:
    return hashlib.sha1(password.encode()).hexdigest()
# Attacker downloads leaked DB and cracks most hashes with precomputed tables.

Secure password storage with Argon2 

# ✅ SECURE: memory-hard hashing with salt
from argon2 import PasswordHasher
ph = PasswordHasher(time_cost=3, memory_cost=65536, parallelism=1)
def store_password(password: str) -> str:
    return ph.hash(password)
def verify_password(stored: str, provided: str) -> bool:
    try:
        ph.verify(stored, provided)
        return True
    except Exception:
        return False

Rate-limited login with account lockout 

// ✅ SECURE Express login flow
const rateLimit = require("express-rate-limit");
const RedisStore = require("rate-limit-redis");
const loginLimiter = rateLimit({
  store: new RedisStore({ client: redisClient }),
  windowMs: 15 * 60 * 1000,
  max: 5,
  skipSuccessfulRequests: true,
  message: { error: "Too many attempts. Try again later." },
});
app.post("/api/login", loginLimiter, async (req, res) => {
  const user = await db.findUserByEmail(req.body.email);
  if (!user || !(await verifyPassword(user.password_hash, req.body.password))) {
    await audit.log({
      event: "failed_login",
      email: req.body.email,
      ip: req.ip,
    });
    return res.status(401).json({ error: "Invalid credentials" });
  }
  if (user.failed_logins >= 5) {
    return res
      .status(403)
      .json({ error: "Account locked. Reset your password." });
  }
  const session = await createSession(user.id, req);
  res.cookie("sid", session.id, {
    httpOnly: true,
    secure: true,
    sameSite: "strict",
  });
  res.json({ ok: true });
});
  • Use memory-hard password hashes: Argon2id, bcrypt, or scrypt.
  • Rate-limit and lock out repeated failed attempts to stop brute force and credential stuffing.
  • Issue sessions as opaque tokens stored server-side; bind them to IP and user-agent fingerprints.
  • Never return stack traces, user-existence hints, or password requirements in login errors.

OAuth 2.0 & OpenID Connect

OAuth 2.0 lets a user grant a third-party application limited access to their resources without sharing their password. OpenID Connect (OIDC) adds an identity layer on top, returning signed ID tokens that prove who the user is.

Real-world example

In 2018, Facebook's "Login with Facebook" feature leaked access tokens for 50 million accounts because a bug in the "View As" feature generated tokens with excessive scopes. It showed how dangerous over-scoped tokens can be.

OAuth 2.0 authorization-code flow (secure version) 

// ✅ SECURE: authorization-code flow with PKCE
const crypto = require("crypto");
// Step 1: Generate PKCE parameters on the client
const codeVerifier = crypto.randomBytes(32).toString("base64url");
const codeChallenge = crypto
  .createHash("sha256")
  .update(codeVerifier)
  .digest("base64url");
const authorizeUrl =
  "https://accounts.google.com/o/oauth2/v2/auth?" +
  new URLSearchParams({
    client_id: CLIENT_ID,
    response_type: "code",
    scope: "openid email profile",
    redirect_uri: "https://app.example.com/callback",
    state: crypto.randomBytes(16).toString("hex"),
    code_challenge: codeChallenge,
    code_challenge_method: "S256",
  });
// Step 2: Exchange code for tokens
const tokenRes = await fetch("https://oauth2.googleapis.com/token", {
  method: "POST",
  headers: { "Content-Type": "application/x-www-form-urlencoded" },
  body: new URLSearchParams({
    client_id: CLIENT_ID,
    client_secret: CLIENT_SECRET,
    code: req.query.code,
    grant_type: "authorization_code",
    redirect_uri: "https://app.example.com/callback",
    code_verifier: codeVerifier,
  }),
});

OIDC token verification in Node.js 

// ✅ SECURE: verify ID token signature and claims
const { jwtVerify, createRemoteJWKSet } = require("jose");
const JWKS = createRemoteJWKSet(
  new URL("https://login.example.com/.well-known/jwks.json"),
);
async function verifyIdToken(idToken, expectedIssuer, expectedClientId) {
  const { payload } = await jwtVerify(idToken, JWKS, {
    issuer: expectedIssuer,
    audience: expectedClientId,
    maxTokenAge: "1 hour",
  });
  return payload; // { sub, email, name, ... }
}
  • Always use PKCE for mobile and SPA OAuth flows to prevent authorization-code interception.
  • Validate ID token issuer, audience, expiry, and signature against the provider's JWKS.
  • Request the minimum scopes needed; over-scoped tokens increase breach blast radius.
  • Store client secrets in environment variables or a KMS, never in client bundles.

Single Sign-On (SSO)

SSO lets users log in once and access multiple applications. Enterprise SSO usually relies on SAML or OIDC, while consumer SSO often uses OAuth/OIDC with Google, GitHub, or Microsoft.

Real-world example

In 2020, the SolarWinds supply-chain attack also compromised SAML signing keys, allowing attackers to forge authentication tokens for Microsoft 365 and Azure AD customers. It demonstrated that SSO is only as strong as the keys that sign its tokens.

SAML response verification (Python) 

# ✅ SECURE: verify SAML signature and conditions
from onelogin.saml2.auth import OneLogin_Saml2_Auth
def saml_callback(request):
    auth = OneLogin_Saml2_Auth(request, custom_settings=saml_settings)
    auth.process_response()
    errors = auth.get_errors()
    if errors:
        raise AuthenticationError(errors)
    if not auth.is_authenticated():
        raise AuthenticationError("SAML assertion not authenticated")
    if auth.get_issuer() != expected_issuer:
        raise AuthenticationError("Wrong issuer")
    email = auth.get_nameid()
    groups = auth.get_attribute("groups")
    return create_session(email, groups)
  • Rotate SAML/OIDC signing keys regularly and monitor for unauthorized certificate changes.
  • Reject unsigned or badly signed SAML assertions; enforce strict issuer and audience validation.
  • Use SP-initiated flows with state parameters to prevent login CSRF.
  • Log every SSO event: success, failure, issuer, and destination application.

Multi-Factor Authentication

MFA requires two or more factors: something you know (password), something you have (phone/security key), or something you are (biometric). It stops most password-only attacks, including credential stuffing and phishing.

Real-world example

In 2019, Microsoft reported that 99.9% of automated attacks against their cloud accounts were blocked simply by enabling MFA. Yet many breaches, including the 2020 Twitter admin-panel incident, succeeded because MFA was not uniformly enforced or was bypassed through social engineering.

TOTP verification in Python 

# ✅ SECURE: time-based one-time password
import pyotp
import time
def verify_totp(secret: str, code: str) -> bool:
    totp = pyotp.TOTP(secret)
    # Allow a small clock skew window
    return totp.verify(code, valid_window=1)
# Store secret encrypted; never expose it after enrollment.

WebAuthn / passkey registration hint 

// ✅ SECURE: prompt for phishing-resistant passkeys
const options = await fetch("/auth/webauthn/register-options").then((r) =>
  r.json(),
);
const credential = await navigator.credentials.create({ publicKey: options });
await fetch("/auth/webauthn/register", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(credential),
});
// Server verifies attestation, origin, challenge, and stores public key.
  • Enforce MFA for all admin, finance, and sensitive operations.
  • Prefer phishing-resistant factors: WebAuthn / passkeys, followed by TOTP apps, then SMS as a last resort.
  • Rate-limit MFA attempts; do not leak whether the password was correct before MFA is checked.
  • Provide recovery codes only once and store them hashed, like passwords.

Role-Based Access Control (RBAC)

RBAC assigns permissions to roles, and roles to users. It is simpler than custom checks in every endpoint and makes audit and revocation easier. A typical application has roles like guest , user , manager , and admin .

Real-world example

In 2019, Capital One's breach involved an IAM role with overly broad S3 permissions. The attacker did not need to "hack" deeply because the role itself could list and read every bucket in the account. This is RBAC done wrong.

RBAC middleware in Express 

// ✅ SECURE: declarative role checks
const ROLES = {
  user: ["read:own_orders"],
  manager: ["read:own_orders", "read:team_orders", "refund:orders"],
  admin: ["read:all_orders", "refund:orders", "manage:users"],
};
function requirePermission(permission) {
  return (req, res, next) => {
    const userPerms = ROLES[req.user.role] || [];
    if (!userPerms.includes(permission)) {
      return res.status(403).json({ error: "Forbidden" });
    }
    next();
  };
}
app.post(
  "/api/orders/:id/refund",
  authenticate,
  requirePermission("refund:orders"),
  refundController,
);

RBAC in a SQL schema 

-- ✅ Minimal RBAC tables
CREATE TABLE roles (
  id SERIAL PRIMARY KEY,
  name TEXT UNIQUE NOT NULL
);
CREATE TABLE permissions (
  id SERIAL PRIMARY KEY,
  name TEXT UNIQUE NOT NULL
);
CREATE TABLE role_permissions (
  role_id INT REFERENCES roles(id) ON DELETE CASCADE,
  permission_id INT REFERENCES permissions(id) ON DELETE CASCADE,
  PRIMARY KEY (role_id, permission_id)
);
CREATE TABLE user_roles (
  user_id INT REFERENCES users(id) ON DELETE CASCADE,
  role_id INT REFERENCES roles(id) ON DELETE CASCADE,
  PRIMARY KEY (user_id, role_id)
);
  • Grant roles the minimum permissions they need (principle of least privilege).
  • Centralize authorization logic so it cannot be skipped in one endpoint.
  • Re-check permissions server-side on every request, even for cached pages.
  • Review role assignments quarterly; remove stale admin grants.

Attribute-Based Access Control (ABAC)

ABAC makes decisions based on attributes of the user, resource, action, and environment. It supports fine-grained policies such as "a manager can approve expenses under $1,000 only during business hours in their own department."

Real-world example

AWS IAM policies are a form of ABAC. The 2017 Accenture AWS exposure happened because an S3 bucket policy included a wildcard principal, effectively letting anyone on the internet access sensitive data. The policy attributes were too permissive.

ABAC policy decision point 

// ✅ SECURE: policy engine for document access
function canViewDocument(user, doc, action) {
  if (user.role === "admin") return true;
  if (user.department !== doc.department) return false;
  if (action === "read") return user.clearance >= doc.classificationLevel;
  if (action === "delete") return user.id === doc.ownerId;
  return false;
}
app.get("/api/documents/:id", authenticate, async (req, res) => {
  const doc = await db.findDocument(req.params.id);
  if (!canViewDocument(req.user, doc, "read")) {
    return res.status(403).json({ error: "Forbidden" });
  }
  res.json(doc);
});
  • Use ABAC when RBAC roles alone are too coarse-grained.
  • Keep policy decisions centralized and auditable.
  • Avoid wildcard permissions in IAM, firewalls, and API scopes.
  • Combine ABAC with RBAC for scalable permission management.

Tokens, Sessions & Secure Storage

After authentication, the server must prove the user's identity on subsequent requests. Common mechanisms are session cookies, JWTs, and OAuth access tokens. Each has different security trade-offs.

Real-world example

In 2018, Reddit disclosed a breach where attackers intercepted SMS-based 2FA and session tokens. The incident showed that storing long-lived tokens without rotation or binding can let attackers stay inside a system for weeks.

Secure session cookie configuration 

// ✅ SECURE: httpOnly + Secure + SameSite cookie
res.cookie("sessionId", session.id, {
  httpOnly: true,
  secure: process.env.NODE_ENV === "production",
  sameSite: "strict",
  maxAge: 24 * 60 * 60 * 1000,
  domain: "app.example.com",
});

JWT with short expiry and refresh rotation 

// ✅ SECURE: access token = 15 min, refresh token = single-use
const accessToken = jwt.sign({ sub: user.id, role: user.role }, ACCESS_SECRET, {
  expiresIn: "15m",
});
const refreshToken = crypto.randomBytes(32).toString("hex");
await db.storeRefreshToken({
  tokenHash: sha256(refreshToken),
  userId: user.id,
  expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000),
  used: false,
});
  • Prefer opaque server-side sessions for high-security applications; JWTs are fine for stateless APIs if short-lived.
  • Never store secrets or tokens in localStorage; use httpOnly cookies.
  • Rotate refresh tokens on every use and revoke them on logout or password change.
  • Bind sessions to device fingerprints and re-authenticate on sensitive actions.

Real-World Breaches in Authentication

Authentication failures are a recurring theme in major breaches. The following table summarizes what went wrong and what control could have prevented or reduced the impact.

Incident Weakness Preventive control
LinkedIn (2012) SHA1 without salt for password hashes. Argon2id/bcrypt with unique per-user salt.
Facebook tokens (2018) Over-scoped access tokens generated by View As bug. Least-privilege scopes, token binding, and logging.
SolarWinds / SAML (2020) Compromised SAML signing keys used to forge SSO tokens. Key rotation, MFA on signing operations, and monitoring.
Twitter admin panel (2020) MFA bypassed via social engineering and broad admin access. Phishing-resistant MFA, least-privilege admin roles, approval workflows.
Capital One IAM role (2019) Overly permissive RBAC role could read all S3 buckets. Least-privilege IAM policies, ABAC conditions, regular access reviews.
Reddit session tokens (2018) Long-lived session tokens intercepted via SMS 2FA bypass. Token rotation, binding, short expiry, and phishing-resistant MFA.

Capstone Project: Secure Identity Platform for a SaaS App

1. What is this project?

You will build a small but realistic identity platform for a fictitious SaaS product called SaaSify . The platform supports password login, "Sign in with Google," TOTP MFA, role-based access control, and audit logging. A set of failing security tests is provided; your goal is to make them pass.

2. What it covers

  • Password authentication with Argon2id hashing, rate limiting, and account lockout.
  • OAuth 2.0 + OpenID Connect login with Google using authorization-code + PKCE.
  • TOTP MFA enrollment and verification with encrypted secrets.
  • RBAC with roles user, manager, admin, and permission middleware.
  • ABAC-style document access: same department + sufficient clearance.
  • Secure session cookies with httpOnly, Secure, SameSite=strict, and short expiry.
  • Token refresh rotation and revocation on logout/password change.
  • Audit logging for every login, role change, and sensitive action.

Step 2 — hardening checklist:

  1. Replace cleartext passwords with Argon2id and add rate-limiting + lockout.
  2. Add session middleware using Redis-backed opaque tokens bound to IP and user-agent.
  3. Implement Google OAuth with PKCE, verify ID tokens with JWKS, and link accounts by email.
  4. Add TOTP enrollment (QR code) and verification; encrypt secrets at rest.
  5. Build RBAC middleware and protect admin routes with admin role.
  6. Add ABAC checks on document routes: department match + clearance level.
  7. Use httpOnly Secure SameSite cookies; implement refresh-token rotation.
  8. Write audit events for login, logout, role changes, MFA enroll, and document access.

4. What did we learn from this capstone project?

Authentication is a chain. A strong password hash is useless if sessions leak; OAuth is useless if tokens are over-scoped; RBAC is useless if one endpoint forgets to check it. The capstone ties together every layer of identity security and shows how to test each layer with automated security tests.

5. How can I enhance this project in the future?

  • Add WebAuthn/passkey registration and login to replace TOTP.
