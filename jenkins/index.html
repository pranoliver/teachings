DevOps Track

Jenkins

Jenkins is the world's most popular open-source automation server. It helps teams build, test, and deploy software continuously. This tutorial takes you from installation to production-grade CI/CD pipelines with real examples, plugins, Docker agents, shared libraries, and a capstone project.

By the end, you will be able to design a complete Jenkins-based delivery pipeline for a Node.js application, including automated testing, security scanning, Docker image builds, and deployment stages.

Why Jenkins?

Jenkins has been around since 2011 and remains dominant because of its huge plugin ecosystem, flexible pipelines, and self-hosted option. It fits organizations that need full control over their CI/CD infrastructure.

1,800+ Plugins

Integrate with GitHub, Docker, Kubernetes, AWS, Azure, SonarQube, Slack, and more.

Pipeline as Code

Store build logic in a Jenkinsfile inside your repository alongside your application code.

Self-Hosted Control

Run Jenkins on your own servers, control secrets, networking, and agent pools.

Distributed Builds

Scale horizontally with agent nodes, Docker containers, or Kubernetes pods.

Real-world example

Netflix uses Jenkins to run tens of thousands of builds per day. By distributing builds across agents and treating pipelines as code, they keep thousands of microservices deployable while maintaining strict compliance and audit requirements.

Installing Jenkins

Jenkins runs on Java. For this tutorial you will install it locally with Docker so the environment is reproducible.

Option A: Docker (recommended) 

# Create a Docker network for Jenkins
docker network create jenkins
# Run Jenkins with persistent volume
docker run -d --name jenkins   --network jenkins   -p 8080:8080 -p 50000:50000   -v jenkins_home:/var/jenkins_home   -v /var/run/docker.sock:/var/run/docker.sock   jenkins/jenkins:lts-jdk17
# Get the initial admin password
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword

Option B: Ubuntu/Debian package 

sudo apt update
sudo apt install openjdk-17-jre-headless -y
curl -fsSL https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key | sudo tee   /usr/share/keyrings/jenkins-keyring.asc > /dev/null
echo deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc]   https://pkg.jenkins.io/debian-stable binary/ | sudo tee   /etc/apt/sources.list.d/jenkins.list > /dev/null
sudo apt update
sudo apt install jenkins -y
sudo systemctl enable --now jenkins

First-time setup checklist

  • Open http://localhost:8080 and paste the initial admin password.
  • Install the suggested plugins (Git, Pipeline, Docker, Blue Ocean).
  • Create the first admin user; do not leave authentication disabled.
  • Configure the Jenkins URL under Manage Jenkins → System.

Your First Jenkins Job

A Freestyle job is the simplest way to start. You point Jenkins at a Git repository, add build steps, and trigger on commits.

Example: Freestyle job configuration

  1. New Item → hello-world → Freestyle project.
  2. Source Code Management → Git → URL: https://github.com/your-org/hello-app.git .
  3. Branches to build: */main .
  4. Build Triggers → Poll SCM: H/5 * * * * .
  5. Build Steps → Execute shell: 
#!/bin/bash
set -e
echo "Building commit ${GIT_COMMIT}"
npm ci
npm test
npm run build

Save and click Build Now . Jenkins clones the repo, runs the shell script, and reports success or failure on the build page. Freestyle jobs are fine for simple tasks, but modern teams prefer Pipeline as Code.

Declarative Pipelines

A Jenkinsfile defines a pipeline in Groovy syntax. Declarative pipelines are the easiest to read and maintain. They include stages, steps, post-actions, and environment variables.

Basic Jenkinsfile 

pipeline {
    agent any
    environment {
        NODE_VERSION = '20'
    }
    stages {
        stage('Checkout') {
            steps {
                git branch: 'main', url: 'https://github.com/your-org/hello-app.git'
            }
        }
        stage('Install') {
            steps {
                sh 'npm ci'
            }
        }
        stage('Test') {
            steps {
                sh 'npm test'
            }
        }
        stage('Build') {
            steps {
                sh 'npm run build'
            }
        }
    }
    post {
        always {
            junit 'reports/**/*.xml'
            cleanWs()
        }
        failure {
            echo 'Pipeline failed. Notify the team.'
        }
    }
}

Conditional and parallel stages 

pipeline {
    agent any
    stages {
        stage('Test Matrix') {
            parallel {
                stage('Unit Tests') {
                    steps {
                        sh 'npm run test:unit'
                    }
                }
                stage('Integration Tests') {
                    steps {
                        sh 'npm run test:integration'
                    }
                }
            }
        }
        stage('Deploy to Staging') {
            when {
                branch 'main'
            }
            steps {
                sh 'scripts/deploy-staging.sh'
            }
        }
    }
}
  • Use agent any for the built-in node, or label specific agents for specialized builds.
  • Keep stages small and focused; each stage should represent one logical step.
  • Use post to publish reports, clean workspaces, and notify channels.
  • Use when to skip stages for pull requests or non-main branches.

Multibranch Pipelines

A Multibranch Pipeline automatically discovers branches and pull requests in a repository and creates a separate Jenkins job for each one. It is the standard way to run Pipeline as Code in Git-based workflows.

Setup steps

  1. New Item → hello-app-multibranch → Multibranch Pipeline.
  2. Branch Sources → GitHub → Repository HTTPS URL and credentials.
  3. Scan Repository Triggers → Periodically if not otherwise run: 1 minute .
  4. Add a Jenkinsfile to your repository root.

Jenkinsfile with PR-specific behavior 

pipeline {
    agent any
    stages {
        stage('Validate') {
            steps {
                sh 'npm ci'
                sh 'npm run lint'
            }
        }
        stage('Test') {
            steps {
                sh 'npm test'
            }
        }
        stage('Build Image') {
            when {
                anyOf {
                    branch 'main'
                    branch 'develop'
                }
            }
            steps {
                script {
                    def image = docker.build("hello-app:${env.BUILD_NUMBER}")
                    image.push()
                }
            }
        }
    }
    post {
        success {
            script {
                if (env.CHANGE_ID) {
                    githubNotify status: 'SUCCESS', context: 'continuous-integration/jenkins'
                }
            }
        }
    }
}

Shared Libraries

Shared libraries let you reuse pipeline logic across many repositories. You write Groovy functions once and call them from any Jenkinsfile.

Library repository structure 

jenkins-shared-library/
├── vars/
│   ├── dockerBuild.groovy
│   ├── runTests.groovy
│   └── notifySlack.groovy
└── src/
    └── com/example/Utils.groovy

vars/dockerBuild.groovy 

def call(Map config = [:]) {
    def imageName = config.imageName ?: error('imageName is required')
    def tag = config.tag ?: env.BUILD_NUMBER
    stage('Build Docker Image') {
        sh "docker build -t ${imageName}:${tag} ."
    }
    stage('Push') {
        withCredentials([usernamePassword(
            credentialsId: 'docker-hub',
            usernameVariable: 'DOCKER_USER',
            passwordVariable: 'DOCKER_PASS'
        )]) {
            sh 'echo $DOCKER_PASS | docker login -u $DOCKER_USER --password-stdin'
            sh "docker push ${imageName}:${tag}"
        }
    }
}

Configure the library

  1. Manage Jenkins → System → Global Pipeline Libraries.
  2. Name: my-shared-library .
  3. Default version: main .
  4. Retrieval method: Modern SCM → GitHub → repository URL.

Use it in a Jenkinsfile 

@Library('my-shared-library') _
pipeline {
    agent any
    stages {
        stage('Build and Push') {
            steps {
                dockerBuild(imageName: 'myorg/hello-app')
            }
        }
    }
}

Agents & Distributed Builds

The built-in controller should not run heavy builds. Agents execute pipeline steps on separate machines or containers, improving security, isolation, and throughput.

Launch a permanent agent 

# On the agent machine, create a jenkins user and directory
sudo useradd -m -s /bin/bash jenkins
sudo mkdir -p /var/jenkins-agent
sudo chown jenkins:jenkins /var/jenkins-agent
# Download the agent JAR from the controller
sudo -u jenkins curl -o /var/jenkins-agent/agent.jar   http://jenkins.example.com:8080/jnlpJars/agent.jar
# Connect to the controller with the secret shown in the node page
sudo -u jenkins java -jar /var/jenkins-agent/agent.jar   -jnlpUrl http://jenkins.example.com:8080/computer/agent-1/jenkins-agent.jnlp   -secret @/var/jenkins-agent/secret-file   -workDir /var/jenkins-agent

Use the agent in a pipeline 

pipeline {
    agent { label 'docker-agent' }
    stages {
        stage('Build') {
            steps {
                sh 'docker build -t myapp:${BUILD_NUMBER} .'
            }
        }
    }
}

Docker agent template 

# docker-compose.agent.yml
version: "3.8"
services:
  jenkins-agent:
    image: jenkins/inbound-agent:latest-jdk17
    environment:
      - JENKINS_URL=http://jenkins:8080
      - JENKINS_SECRET=
      - JENKINS_AGENT_NAME=docker-agent-1
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock

Plugins & Security

Plugins extend Jenkins, but they are also a major attack surface. Keep them updated, remove unused ones, and follow the principle of least privilege.

Plugin Purpose
Pipeline Jenkinsfile support and stage visualization.
GitHub Branch Source Multibranch pipelines from GitHub repos and PRs.
Docker Pipeline Build, run, and push Docker images from pipelines.
Credentials Binding Inject secrets safely into builds.
JUnit Publish test results and trends.
SonarQube Scanner Static analysis and code quality gates.
Slack Notification Post build results to Slack channels.

Store credentials securely 

pipeline {
    agent any
    environment {
        SONAR_TOKEN = credentials('sonar-token')
    }
    stages {
        stage('Scan') {
            steps {
                sh 'npx sonarqube-scanner -Dsonar.login=$SONAR_TOKEN'
            }
        }
    }
}
  • Run Jenkins with a dedicated non-root OS user and minimal file permissions.
  • Disable anonymous access and use LDAP, SSO, or matrix-based security.
  • Enable CSRF protection and Content Security Policy headers.
  • Audit plugins monthly; remove unused plugins to reduce attack surface.

Jenkins + Docker

Running builds inside Docker containers guarantees reproducible environments. The Jenkins controller can spawn agents as Docker containers and pipelines can build application images from Dockerfiles.

Dockerfile for a custom agent 

# Dockerfile.agent
FROM jenkins/inbound-agent:latest-jdk17
USER root
RUN apt-get update && apt-get install -y     docker.io     nodejs     npm     && rm -rf /var/lib/apt/lists/*
USER jenkins

Build and push in a pipeline 

pipeline {
    agent any
    stages {
        stage('Checkout') {
            steps {
                git branch: 'main', url: 'https://github.com/your-org/hello-app.git'
            }
        }
        stage('Test') {
            steps {
                sh 'npm ci'
                sh 'npm test'
            }
        }
        stage('Build Image') {
            steps {
                script {
                    def image = docker.build("myorg/hello-app:${env.BUILD_NUMBER}")
                    docker.withRegistry('https://registry.hub.docker.com', 'docker-hub') {
                        image.push()
                        image.push('latest')
                    }
                }
            }
        }
    }
}

Docker-in-Docker warning

Mounting /var/run/docker.sock is convenient but breaks container isolation. For untrusted workloads, use Kaniko, BuildKit in rootless mode, or separate ephemeral VMs.

Production Hardening

A production Jenkins controller must be reliable, observable, and secure. Backups, monitoring, and access control are non-negotiable.

Backups

Back up $JENKINS_HOME daily. Test restores. Store secrets in a credential manager, not in job config XML.

Monitoring

Export metrics with the Prometheus plugin. Alert on queue length, disk usage, failed builds, and plugin CVEs.

RBAC

Use the Role-based Authorization Strategy plugin. Developers see their jobs; admins manage the controller.

Updates

Keep Jenkins core and plugins current. Run test upgrades in a staging controller first.

Backup script 

#!/bin/bash
# jenkins-backup.sh
JENKINS_HOME=/var/lib/jenkins
BACKUP_DIR=/backups/jenkins/$(date +%Y%m%d_%H%M%S)
mkdir -p "$BACKUP_DIR"
tar --exclude='*/workspace/*' --exclude='*/builds/*'     -czf "$BACKUP_DIR/jenkins_home.tar.gz" -C "$JENKINS_HOME" .
# Keep only the last 7 backups
ls -1td /backups/jenkins/* | tail -n +8 | xargs -r rm -rf

Troubleshooting

Symptom Likely cause Fix
Build fails on agent only Missing tool or different environment. Use the same Docker image on all agents; lock tool versions.
Disk full Workspace, artifacts, or logs accumulating. Enable Discard old builds and use cleanWs() in pipelines.
Plugins fail to load Version mismatch or dependency conflict. Use the Plugin Version Pinning plugin and test updates.
Pipeline hangs Input step waiting forever or agent disconnected. Set timeouts on stages and agents; use timeout step.

Capstone Project: Full CI/CD for a Node.js API

1. What is this project?

You will set up a complete Jenkins-based CI/CD pipeline for a Node.js/Express API. The pipeline runs on every commit, executes tests, performs security scanning, builds a Docker image, and deploys to a staging environment. A production deployment stage requires manual approval.

2. What it covers

  • Jenkins installation with Docker and a dedicated agent.
  • Multibranch pipeline scanning a GitHub repository.
  • Declarative Jenkinsfile with install, lint, test, and build stages.
  • Parallel unit and integration test execution.
  • Docker image build and push to a registry.
  • SonarQube static analysis and quality gate.
  • OWASP Dependency-Check for vulnerable libraries.
  • Deployment to staging with environment variables and secrets.
  • Manual approval gate before production deployment.
  • Slack notifications and JUnit test result publishing.

3. How it is done

Project layout: 

node-api/
├── Dockerfile
├── docker-compose.yml
├── Jenkinsfile
├── package.json
├── src/
│   └── server.js
├── tests/
│   ├── unit/
│   └── integration/
└── scripts/
    ├── deploy-staging.sh
    └── deploy-production.sh

Step 1 — install Jenkins and an agent: 

# Start the controller
docker run -d --name jenkins   -p 8080:8080 -p 50000:50000   -v jenkins_home:/var/jenkins_home   -v /var/run/docker.sock:/var/run/docker.sock   jenkins/jenkins:lts-jdk17
# Build and run a custom agent image
docker build -t jenkins-node-agent -f Dockerfile.agent .
docker run -d --name jenkins-agent   --network host   -v /var/run/docker.sock:/var/run/docker.sock   jenkins-node-agent   -url http://$(hostname -I | awk '{print $1}'):8080   -workDir /home/jenkins/agent   -secret    -name node-agent-1

Step 2 — create the Jenkinsfile: 

pipeline {
    agent { label 'node-agent' }
    environment {
        NODE_VERSION = '20'
        IMAGE_NAME = 'myorg/node-api'
        SONAR_TOKEN = credentials('sonar-token')
        DOCKER_REGISTRY = 'https://index.docker.io/v1/'
    }
    options {
        buildDiscarder(logRotator(numToKeepStr: '10'))
        timeout(time: 30, unit: 'MINUTES')
    }
    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }
        stage('Install & Lint') {
            steps {
                sh 'npm ci'
                sh 'npm run lint'
            }
        }
        stage('Test') {
            parallel {
                stage('Unit') {
                    steps {
                        sh 'npm run test:unit -- --reporter=xunit --reporter-option=output=reports/unit.xml'
                    }
                }
                stage('Integration') {
                    steps {
                        sh 'npm run test:integration -- --reporter=xunit --reporter-option=output=reports/integration.xml'
                    }
                }
            }
        }
        stage('Security Scan') {
            steps {
                sh 'npm audit --audit-level=moderate'
                sh 'npx dependency-check --project node-api --scan ./package-lock.json --out reports/dependency-check'
            }
        }
        stage('SonarQube Analysis') {
            steps {
                withSonarQubeEnv('sonarqube-server') {
                    sh 'npx sonarqube-scanner -Dsonar.login=$SONAR_TOKEN'
                }
                timeout(time: 5, unit: 'MINUTES') {
                    waitForQualityGate abortPipeline: true
                }
            }
        }
        stage('Build & Push Image') {
            when {
                anyOf {
                    branch 'main'
                    branch 'develop'
                }
            }
            steps {
                script {
                    def image = docker.build("${env.IMAGE_NAME}:${env.BUILD_NUMBER}")
                    docker.withRegistry(env.DOCKER_REGISTRY, 'docker-hub-creds') {
                        image.push()
                        image.push(env.BRANCH_NAME == 'main' ? 'latest' : 'dev')
                    }
                }
            }
        }
        stage('Deploy to Staging') {
            when {
                branch 'main'
            }
            steps {
                withCredentials([string(credentialsId: 'staging-api-key', variable: 'API_KEY')]) {
                    sh 'scripts/deploy-staging.sh ${BUILD_NUMBER} ${API_KEY}'
                }
            }
        }
        stage('Production Approval') {
            when {
                branch 'main'
            }
            steps {
                input message: 'Deploy to production?', ok: 'Deploy'
            }
        }
        stage('Deploy to Production') {
            when {
                branch 'main'
            }
            steps {
                withCredentials([string(credentialsId: 'prod-api-key', variable: 'API_KEY')]) {
                    sh 'scripts/deploy-production.sh ${BUILD_NUMBER} ${API_KEY}'
                }
            }
        }
    }
    post {
        always {
            junit 'reports/**/*.xml'
            publishHTML([
                allowMissing: false,
                alwaysLinkToLastBuild: true,
                keepAll: true,
                reportDir: 'reports/dependency-check',
                reportFiles: 'dependency-check-report.html',
                reportName: 'Dependency Check Report'
            ])
            cleanWs()
        }
        success {
            slackSend(color: 'good', message: "SUCCESS: ${env.JOB_NAME} ${env.BUILD_NUMBER}")
        }
        failure {
            slackSend(color: 'danger', message: "FAILURE: ${env.JOB_NAME} ${env.BUILD_NUMBER}")
        }
    }
}

Step 3 — deployment scripts: 

# scripts/deploy-staging.sh
#!/bin/bash
set -e
BUILD_NUMBER=$1
API_KEY=$2
docker pull myorg/node-api:${BUILD_NUMBER}
docker stop node-api-staging || true
docker rm node-api-staging || true
docker run -d --name node-api-staging   -e API_KEY=${API_KEY}   -p 8081:3000   myorg/node-api:${BUILD_NUMBER}
# Health check
curl -sf http://localhost:8081/health || exit 1
echo "Staging deployment complete"

Step 4 — required Jenkins configuration:

  1. Install plugins: Pipeline, GitHub Branch Source, Docker Pipeline, Credentials Binding, JUnit, SonarQube Scanner, OWASP Dependency-Check, Slack Notification, Role-based Authorization Strategy.
  2. Create credentials: docker-hub-creds , sonar-token , staging-api-key , prod-api-key .
  3. Configure a SonarQube server under Manage Jenkins → System.
  4. Add an agent with label node-agent .
  5. Create a Multibranch Pipeline pointing at your GitHub repository.

4. What did we learn from this capstone project?

A production CI/CD pipeline is more than running tests. It is a chain of verification, security, packaging, deployment, and governance. Jenkins provides the building blocks, but the pipeline design must enforce quality gates, protect secrets, and keep the controller secure. The capstone shows how every stage reinforces the next: tests catch bugs early, security scans prevent vulnerable artifacts, and manual approvals control production risk.

5. How can I enhance this project in the future?

  • Replace Docker-in-Docker with Kaniko or BuildKit rootless builds for stronger isolation.
  • Add Kubernetes agents with the Kubernetes plugin for elastic scaling.
  • Implement configuration-as-code (JCasC) to version-control all Jenkins settings.
  • Add smoke tests and canary deployments with traffic splitting.
  • Integrate with a service mesh or feature flags for progressive rollouts.
  • Export pipeline metrics to Prometheus and build a Grafana CI/CD dashboard.
