Fine-Tuning Large Language Models

AI-4

Introduction to Fine-Tuning

Fine-tuning adapts a language model to a specific task, tone, or format without training a model from scratch. In this tutorial you will fine-tune a small local model to answer support questions in the style of Nimbus Cloud Solutions : concise, friendly, and consistent. We use LoRA so training is fast and memory-efficient, and we deploy the result through Ollama.

RAG vs. fine-tuning

  • RAG gives the model facts from documents.
  • Fine-tuning shapes how the model writes and behaves.
  • They work together: use RAG for current facts and a fine-tuned model for brand voice.

What you will build

A Streamlit chatbot that compares the base model against your fine-tuned model side by side. You will see how fine-tuning makes answers shorter, more consistent, and aligned with Nimbus support style.

Environment Setup

Fine-tuning needs more packages than RAG, but everything still runs locally. Apple Silicon, a modest NVIDIA GPU, or even CPU works for the small LoRA run we demonstrate.

1. Install Ollama and the base model

# or
ollama pull qwen2.5:7b

A 7B–8B parameter model is small enough to fine-tune and serve locally. You can also continue with kimi-k2.7-code:cloud if it supports Modelfile-based GGUF serving.

2. Create a project folder with uv

3. Install Python packages

The Nimbus Support Dataset

Load and split 

from datasets import load_dataset

dataset = load_dataset("json", data_files="nimbus_support_ft.jsonl", split="train")
dataset = dataset.train_test_split(test_size=0.1, seed=42)
train = dataset["train"]
val = dataset["test"]
print(f"Train: {len(train)}, Validation: {len(val)}")

Save as load_dataset.py and run: uv run load_dataset.py

Conversation Formatting

Models do not understand JSON. We must turn each conversation into a single text string using a chat template. Modern instruction-tuned models expect special tokens around user and assistant turns. 

from transformers import AutoTokenizer

model_name = "meta-llama/Meta-Llama-3.1-8B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token

def format_messages(example):
    text = tokenizer.apply_chat_template(
        example["messages"], tokenize=False, add_generation_prompt=False
    )
    return {"text": text}

train_formatted = train.map(format_messages)
print(train_formatted[0]["text"][:300])

Save as format_messages.py and run: uv run format_messages.py

If you use a local GGUF through Ollama later, make sure the base model you download matches the chat template used during training, or responses may look malformed.

LoRA / QLoRA Concepts

Fine-tuning every weight of an 8B model would need hundreds of gigabytes of GPU memory. LoRA freezes the base weights and trains small adapter layers inserted into the attention blocks. QLoRA goes further by loading the base model in 4-bit precision.

Key hyperparameters

  • r (rank): how much capacity each adapter has. Common values are 8, 16, or 32.
  • alpha : scaling factor for the adapter output. Often set to 2 * r.
  • lora_dropout : regularization to avoid overfitting. 0.05 is a typical starting point.
  • target_modules : which layers get adapters. Usually q_proj and v_proj. 
from peft import LoraConfig, get_peft_model

lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "v_proj", "k_proj", "o_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)

model = get_peft_model(base_model, lora_config)
model.print_trainable_parameters()

Save as lora_config.py and run: uv run lora_config.py

Training Loop

The training loop minimizes the cross-entropy loss on the assistant tokens in each conversation. We use the TRL library's SFTTrainer because it handles chat templates, padding, and packing automatically. 

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
from peft import LoraConfig
from trl import SFTTrainer

model_name = "meta-llama/Meta-Llama-3.1-8B-Instruct"

# Load base model in 4-bit for QLoRA
from transformers import BitsAndBytesConfig
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,
    bnb_4bit_quant_type="nf4",
)

base_model = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=bnb_config,
    device_map="auto",
    torch_dtype=torch.bfloat16,
)

tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token
tokenizer.padding_side = "right"

lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "v_proj", "k_proj", "o_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)

training_args = TrainingArguments(
    output_dir="nimbus-lora",
    num_train_epochs=3,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=4,
    optim="paged_adamw_8bit",
    learning_rate=2e-4,
    logging_steps=10,
    eval_strategy="epoch",
    save_strategy="epoch",
    bf16=torch.cuda.is_bf16_supported(),
    fp16=not torch.cuda.is_bf16_supported(),
)

trainer = SFTTrainer(
    model=base_model,
    train_dataset=train_formatted,
    eval_dataset=val.map(format_messages),
    peft_config=lora_config,
    tokenizer=tokenizer,
    args=training_args,
    dataset_text_field="text",
    max_seq_length=512,
)

trainer.train()
trainer.save_model("nimbus-lora-final")

Save as train.py and run: uv run train.py

Apple Silicon / CPU note

On Apple Silicon, set device_map={"": "mps"} and remove the BitsAndBytesConfig. On CPU, training is possible but a single epoch can take hours. Reduce epochs to 1 and the dataset to 50 examples for a quick proof of concept.

Evaluation

After training, evaluate whether the fine-tuned model actually learned the Nimbus support style. We compare outputs from the base and fine-tuned models on held-out questions. 

from peft import PeftModel

# Merge adapter into base model for easier inference
merged = PeftModel.from_pretrained(base_model, "nimbus-lora-final")
merged = merged.merge_and_unload()
merged.save_pretrained("nimbus-merged")
tokenizer.save_pretrained("nimbus-merged")

# Generate a test response
def generate(model, prompt, max_new_tokens=120):
    inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
    outputs = model.generate(**inputs, max_new_tokens=max_new_tokens, do_sample=False)
    return tokenizer.decode(outputs[0], skip_special_tokens=True)

test_prompt = "How do I reset my password?"
print(generate(merged, f"User: {test_prompt}\nAssistant:"))

Save as merge_model.py and run: uv run merge_model.py

Metrics to watch

  • Validation loss : should decrease and stabilize.
  • Output style : answers should be concise, friendly, and include Nimbus-specific details.
  • Consistency : repeated questions should produce similar structure.

Loading with Ollama

Ollama runs GGUF models through a simple Modelfile. After merging the adapter, export the model to GGUF with llama.cpp, then create an Ollama model.

Export to GGUF 

# Install llama.cpp conversion tools if needed
uv add llama-cpp-python

# Convert the merged HF model to GGUF (Q4_K_M is a good default)
uv run python convert_hf_to_gguf.py nimbus-merged --outfile nimbus-q4.gguf --outtype q4_k_m

Save as format_messages.py and run: uv run format_messages.py

Save as lora_config.py and run: uv run lora_config.py

Save as train.py and run: uv run train.py

Save as merge_model.py and run: uv run merge_model.py

Create an Ollama Modelfile 

FROM ./nimbus-q4.gguf

PARAMETER temperature 0.3
PARAMETER top_p 0.9

SYSTEM """You are a helpful Nimbus Cloud Solutions support assistant.
Answer briefly, accurately, and in a friendly tone."""

TEMPLATE """{{- if .System }}{{ .System }}{{ end }}
{{- range .Messages }}
{{- if eq .Role "user" }}User: {{ .Content }}
{{- else if eq .Role "assistant" }}Assistant: {{ .Content }}
{{- end }}
{{- end }}Assistant:"""

Build and run 

ollama create nimbus-support -f Modelfile

Capstone: Streamlit Chat Comparison

The capstone is a 5-phase project that creates a side-by-side chat comparison. All commands below use uv for environment and dependency management. Users can type a Nimbus support question and see how the base model and the fine-tuned model respond differently.

Phase 1: Project setup with uv

Open a terminal, create a dedicated folder, and set up a uv-managed virtual environment with all required packages. 

uv init nimbus-finetune
cd nimbus-finetune
uv venv
source .venv/bin/activate  # Windows: .venv\Scripts\activate

# Download the Nimbus support fine-tuning dataset
# (Download button is in Section 3 of this tutorial)
cp /path/to/downloads/nimbus_support_ft.jsonl ./nimbus_support_ft.jsonl

uv add torch transformers datasets peft accelerate bitsandbytes trl ollama streamlit tqdm

# Pull the base model in Ollama
ollama pull llama3.1:8b

Save the training script and Streamlit app in this folder. Run training with uv run python train.py .

Phase 2: Prepare the comparison prompt

Use the same user question and system prompt for both models so the only variable is the model.

Phase 3: Generation helpers

Write a helper function that calls Ollama with a model name, prompt, and system message, then returns the generated text.

Phase 4: Streamlit layout

Create two columns: left for the base model llama3.1:8b and right for the fine-tuned model nimbus-support .

Phase 5: Full app code 

import streamlit as st
import ollama

BASE_MODEL = "llama3.1:8b"
FT_MODEL = "nimbus-support"
SYSTEM = (
    "You are a helpful Nimbus Cloud Solutions support assistant. "
    "Answer briefly, accurately, and in a friendly tone."
)

st.set_page_config(page_title="Nimbus Fine-Tuning Demo", layout="wide")
st.title("Nimbus Support: Base vs. Fine-Tuned Model")
st.caption("Compare the base Llama 3.1 model with the Nimbus-tuned model.")


def generate(model, question):
    response = ollama.generate(
        model=model,
        system=SYSTEM,
        prompt=question,
        options={"temperature": 0.3, "top_p": 0.9},
    )
    return response["response"]


question = st.text_input(
    "Ask a Nimbus support question:",
    "What happens if I exceed my API limit?",
)

if st.button("Compare models"):
    col1, col2 = st.columns(2)
    with st.spinner("Generating answers..."):
        base_answer = generate(BASE_MODEL, question)
        ft_answer = generate(FT_MODEL, question)

    with col1:
        st.header("Base Model")
        st.write(base_answer)

    with col2:
        st.header("Fine-Tuned Model")
        st.success(ft_answer)

st.markdown("""
**What to look for:**
- The fine-tuned model should answer in the Nimbus style and include specific Nimbus facts.
- The base model may give a generic answer or ask for clarification.
""")

Save as compare.py and run: uv run compare.py

Phase 6: Run the capstone with uv

Use uv run to launch Streamlit so the correct environment is always used, even if you forget to activate the virtual environment. 

uv run streamlit run compare.py

Before running the app, make sure the fine-tuned model is available in Ollama: ollama create nimbus-support -f Modelfile.
