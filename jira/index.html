2. Why Jira?

Jira is the most widely used issue and project tracking tool in software teams. It supports Scrum, Kanban, and hybrid processes, and it connects planning, development, and operations in one place.

  • Backlog & boards — prioritize work visually with drag-and-drop boards.
  • Sprints & releases — plan iterations, track velocity, and ship predictably.
  • Custom workflows — model your real process: Todo → In Progress → Review → Done.
  • Automation — trigger actions on events without writing code.
  • Integrations — link GitHub, Bitbucket, Slack, Confluence, Jenkins, and hundreds more.

When to choose Jira: any team that needs structured issue tracking, sprint planning, or cross-team visibility. For lightweight personal tasks, simpler tools like Trello or GitHub Issues may be faster.

3. Setup & Installation

The easiest way to start is Jira Cloud . Atlassian offers a free plan for up to 10 users. You can also run Jira Data Center locally with Docker for evaluation.

Option A: Jira Cloud (recommended)

  1. Go to atlassian.com/software/jira and click Try it free .
  2. Create an Atlassian account or sign in with Google.
  3. Choose a site name, e.g. yourteam.atlassian.net .
  4. Select a project template: Scrum, Kanban, or Bug tracking.

Option B: Jira Data Center via Docker 

# Create a persistent volume for Jira data
docker volume create jira-data

# Run Jira Software Data Center evaluation
docker run -d --name jira \
  -p 8080:8080 \
  -v jira-data:/var/atlassian/application-data/jira \
  atlassian/jira-software:latest

# Follow setup wizard at http://localhost:8080
# Default license: request a trial from Atlassian

The first startup takes a few minutes. Once the setup wizard appears, choose I'll set it up myself , connect a PostgreSQL database for production use, and enter a trial license.

4. Your First Project

A Jira project is the workspace for a product or team. The template you pick defines the default issue types, board, and workflow.

Create a Scrum project

  1. From the top navigation, click Projects → Create project .
  2. Select Scrum under Software development .
  3. Name the project Orbit SaaS and choose a key such as ORB .
  4. Click Create project .

Jira creates a backlog, a Scrum board, and default issue types. You can customize everything later.

Configure issue types

Issue types group work by purpose. A common hierarchy for SaaS teams is:

  • Epic — large initiative that spans multiple sprints.
  • Story — user-facing deliverable.
  • Task — technical or operational work.
  • Bug — defect to fix.
  • Sub-task — child of a story or task.

To add custom fields, go to Project settings → Issue types and then Fields . Common custom fields include Acceptance Criteria , Sprint Goal , and Story Points .

5. Issues, Epics & Stories

Issues are the core unit of work. Good issue hygiene keeps a team aligned and makes reporting meaningful.

Anatomy of a great issue 

Summary: User can reset password via email
Issue Type: Story
Priority: Medium
Assignee: alex.chen
Reporter: product@example.com
Labels: auth, onboarding
Components: API, Web
Story Points: 5

Description:
As a registered user,
I want to reset my password from the login page,
so that I can regain access without contacting support.

Acceptance Criteria:
1. "Forgot password" link appears on /login.
2. System sends a signed, time-limited token to the email.
3. Token link opens a secure reset form.
4. New password must meet policy requirements.
5. Old sessions are invalidated after reset.

Linking issues

Use issue links to express relationships. A story can belong to an Epic , a bug can block a feature, and a task can duplicate another issue. To add a link, open an issue, click Link issue , and choose the relationship.

REST API example: create an issue 

# Replace {site}, {email}, and {token} with your values
# Generate an API token at id.atlassian.com/manage-profile/security/api-tokens

curl -X POST https://{site}.atlassian.net/rest/api/3/issue \
  -u {email}:{token} \
  -H "Content-Type: application/json" \
  -d '{
    "fields": {
      "project": { "key": "ORB" },
      "summary": "Add password reset endpoint",
      "issuetype": { "name": "Story" },
      "assignee": { "accountId": "5b10ac8d82e05b22cc7d4ef5" },
      "description": {
        "type": "doc",
        "version": 1,
        "content": [
          {
            "type": "paragraph",
            "content": [{ "type": "text", "text": "Implement a secure password reset flow." }]
          }
        ]
      }
    }
  }'

The response contains the new issue key, e.g. ORB-42 . Store it for CI/CD or Slack notifications.

6. Boards & Sprints

Boards make work visible. A Scrum board adds sprint planning and velocity tracking; a Kanban board focuses on continuous flow and WIP limits.

Scrum board basics

  1. Open your project and click Backlog .
  2. Click Create sprint and name it Orbit Sprint 1 .
  3. Drag issues from the backlog into the sprint.
  4. Click Start sprint , set a duration and goal, then confirm.
  5. Move issues across columns as they progress.
  6. At the end, click Complete sprint and review the burndown chart.

Kanban WIP limits

In Kanban, set a maximum number of issues per column. When a column hits its limit, the team stops starting new work and focuses on finishing. To configure WIP limits, click the three dots on a column and select Set column constraint . 

# Example board column setup for a SaaS team
Columns:
  - To Do        # WIP limit: 10
  - In Progress  # WIP limit: 4
  - Code Review  # WIP limit: 3
  - Testing      # WIP limit: 2
  - Done

7. Workflows

A workflow defines the statuses an issue can have and the transitions between them. You can use the default simplified workflow or create a custom one.

Sample custom workflow 

Statuses:
  - To Do
  - In Progress
  - In Review
  - Ready for Test
  - Testing
  - Done
  - Reopened

Transitions:
  Start work:        To Do → In Progress
  Submit for review: In Progress → In Review
  Request changes:   In Review → In Progress
  Approve:           In Review → Ready for Test
  Begin testing:     Ready for Test → Testing
  Pass tests:        Testing → Done
  Fail tests:        Testing → Reopened
  Reopen:            Done → Reopened
  Resume:            Reopened → In Progress

Validators:
  - In Review requires linked PR or branch
  - Ready for Test requires code review approval

To apply a custom workflow, go to Project settings → Workflows and associate the workflow with the relevant issue types. Add conditions (who can transition), validators (what must be true), and post functions (what happens after) to enforce quality gates.

Transition screens

A transition screen prompts users for information during a transition. For example, when moving to Done , you can require a Resolution and Fix version .

8. JQL Search

JQL (Jira Query Language) lets you build precise filters, boards, and dashboards. It looks like SQL but is tailored to Jira's data model.

Common JQL queries 

# Open high-priority bugs in the current sprint
project = ORB AND issuetype = Bug
  AND priority IN (High, Highest)
  AND sprint in openSprints() AND status != Done

# Stories assigned to me that are overdue
project = ORB AND issuetype = Story
  AND assignee = currentUser()
  AND duedate < now() AND status != Done

# Unestimated backlog items ready for sprint planning
project = ORB AND sprint is EMPTY
  AND "Story Points" is EMPTY AND status = "To Do"

# Recently closed issues with linked support tickets
project = ORB AND status = Done
  AND resolved >= -7d AND labels = support

# Epics with unresolved children
project = ORB AND issuetype = Epic
  AND status != Done AND "Epic Link" is not EMPTY

Save a JQL query as a filter and reuse it across boards, dashboards, subscriptions, and automation rules.

Useful JQL functions

  • currentUser() — issues assigned to the viewer.
  • openSprints() / closedSprints() — active or past sprints.
  • startOfWeek() / endOfMonth() — relative date ranges.
  • watchedIssues() — issues the current user watches.

9. Automation Rules

Jira Automation uses a trigger-condition-action model. You can build rules visually, and each project has a generous free quota on Cloud.

Example: auto-assign bugs by component 

Rule: Auto-assign infrastructure bugs
Trigger: Issue created
Condition:
  - issueType = Bug
  - component = Infrastructure
Action:
  - Assign issue to user: ops-lead@example.com
  - Add comment: "Thanks for reporting. The infrastructure team has been notified."
  - Transition issue to: Triaged

Example: close linked issues when PR merges

With the GitHub for Jira integration, you can create a rule that transitions issues to Done when a linked pull request is merged.

  1. Install the GitHub for Jira app from Atlassian Marketplace.
  2. Connect your GitHub organization and repositories.
  3. Developers include issue keys in branch or PR titles, e.g. ORB-42 add password reset .
  4. Create an automation rule: When: Pull request merged → For: Linked issues → Then: Transition to Done .

Other popular automations include: daily Slack summaries, stale-issue reminders, sprint-start notifications, and auto-creating sub-tasks when a story enters In Progress .

10. Reports & Dashboards

Jira ships with built-in Agile reports. Dashboards let you combine multiple gadgets for cross-project visibility.

Essential reports

  • Burndown chart — work remaining vs. ideal trend during a sprint.
  • Velocity chart — story points completed per sprint for capacity planning.
  • Cumulative flow diagram — where work gets stuck over time.
  • Control chart — cycle time and lead time distribution.
  • Sprint report — scope changes and completion metrics.

Building a dashboard

  1. Go to Dashboards → Create dashboard .
  2. Name it Engineering Health and set sharing to the engineering team.
  3. Add gadgets such as: Filter results , Assigned to me , Agile sprint health , and Pie chart by status .
  4. Configure each gadget with a saved JQL filter.
# Engineering Health dashboard filters
Open bugs:           project = ORB AND issuetype = Bug AND status != Done
Sprint backlog:      project = ORB AND sprint in openSprints() ORDER BY priority DESC
Unassigned work:     project = ORB AND assignee is EMPTY AND status != Done
This week closed:    project = ORB AND status changed to Done after startOfWeek()

11. Advanced Topics

Roadmaps

Jira Premium and Cloud Standard offer a timeline view that rolls up epics, dependencies, and releases. Use it for quarterly planning and to surface cross-team dependencies before they block sprints.

Permissions and roles

Jira permissions are layered: Global permissions (site-wide), Project permissions (per project), and Issue security (per issue). Use groups and project roles to avoid granting access one user at a time.

Integrations

  • GitHub / Bitbucket — link branches, commits, and PRs to issues.
  • Slack — get notifications and create issues from channels.
  • Confluence — store requirements and retrospectives.
  • Jenkins / GitHub Actions — update issues from build results.

REST API: search with JQL 

curl -s -u {email}:{token} \
  -X POST https://{site}.atlassian.net/rest/api/3/search \
  -H "Content-Type: application/json" \
  -d '{
    "jql": "project = ORB AND status != Done ORDER BY priority DESC",
    "fields": ["summary", "status", "assignee", "issuetype"],

12. Best Practices

  • Keep issue titles actionable. "Add password reset endpoint" is clearer than "Password stuff".
  • One concern per issue. Split large requests into stories and tasks that fit a sprint.
  • Use a single source of truth. Put requirements in the issue or linked Confluence page, not scattered across chat.
  • Estimate consistently. Use story points or time, but pick one method and calibrate with the team.
  • Review workflows quarterly. Remove unused statuses and fix bottlenecks revealed by the control chart.
  • Automate the boring parts. Let rules handle assignments, notifications, and state transitions so humans focus on decisions.

Anti-pattern to avoid: creating a status for every micro-step. A workflow with 15 statuses slows the board down. Aim for 4–7 meaningful states and use fields or comments for detail.

13. Capstone Project: Launch "Orbit" SaaS with Jira

You are the delivery lead for Orbit , a new team collaboration SaaS. Use Jira to plan the MVP launch, run two sprints, and report progress to stakeholders.

Phase 1: Set up the project

  • Create a Scrum project named Orbit SaaS with key ORB .
  • Configure issue types: Epic, Story, Task, Bug, and Sub-task.
  • Add custom fields: Story Points (number), Acceptance Criteria (textarea), and Customer Segment (single-select: SMB, Enterprise, Internal).
  • Invite three fake teammates as project members with Developer and Viewer roles.

Phase 2: Build the backlog

  • Create three epics: User Authentication , Team Workspaces , and Billing .
  • Under each epic, create 3–5 stories with summaries, acceptance criteria, and story points.
  • Prioritize the backlog using drag-and-drop. Place authentication first because other features depend on it.
  • Assign one story per team member and label stories by customer segment.

Phase 3: Run a sprint

  • Create a two-week sprint named Orbit Sprint 1 with a clear sprint goal.
  • Move the top 10–12 story points into the sprint and start it.
  • Configure the board columns: To Do, In Progress, In Review, Testing, Done.
  • Move at least one story through every column during the sprint and complete the sprint.
  • Review the burndown and velocity charts and record the team's velocity.

Phase 4: Automation, JQL, and dashboards

  • Create an automation rule that assigns new bugs to the QA lead and adds a triage comment.
  • Write four saved JQL filters: open bugs, current sprint backlog, my issues, and recently closed.
  • Build a dashboard named Orbit Engineering Health using your filters.
  • Export the dashboard URL and share it in a mock stakeholder update.

Phase 5: Integration and retrospective

  • Connect a GitHub repository to the project (or simulate with issue links).
  • Create a second sprint with scope based on the velocity from Sprint 1.
  • Run a retrospective in Confluence or a Jira issue: document what went well, what slowed the team down, and one workflow improvement.
  • Adjust the board workflow based on the retrospective finding and document the change.
