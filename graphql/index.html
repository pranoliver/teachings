Chapter 2

Why GraphQL?

REST APIs are great, but they often return too much or too little data. Clients may need multiple round-trips to assemble the right information. GraphQL solves this with a single endpoint and a flexible query language.

REST vs GraphQL 

// Multiple
REST endpoints GET /users/1 GET /users/1/posts GET /users/1/followers // Then
manually combine responses const user = await fetchUser(1);
const posts = await fetchPosts(1);
const followers = await fetchFollowers(1);
// Single
GraphQL query query
{ user(id: 1)
{ name posts
{ title }
followers
{ name }
} }

Key advantages

  • Request only the fields you need.
  • Fetch nested related data in one request.
  • Strongly typed schema documents the API.
  • Introspection lets tools auto-generate clients.

Setup & Schema

A GraphQL schema defines what data is available and how clients can interact with it. The schema is the contract between client and server. 

npm init -y 
npm install 
express 
express-graphql graphql cnpm install --save-dev nodemon
const express = require("express");
const { graphqlHTTP } = require("express-graphql");
const { buildSchema } = require("graphql");
const schema = buildSchema(` type Query { hello: String } `);
const root = { hello: () => "Hello, GraphQL!" };
const app = express();
app.use("/graphql", graphqlHTTP({ schema, rootValue: root, graphiql: true }));
app.listen(4000, () =>
  console.log("Server running on http://localhost:4000/graphql"),
);

Chapter 4

Queries

Queries fetch data from a GraphQL server. You specify the exact shape of the response, including nested fields. 

query {
  user(id: "1") {
    id
    name
    email
    posts {
      title
      published
    }
  }
}
{
  "data": {
    "user": {
      "id": "1",
      "name": "Ada Lovelace",
      "email": "ada@example.com",
      "posts": [{ "title": "Intro to GraphQL", "published": true }]
    }
  }
}

Query features

  • Fields: select exactly what you need.
  • Arguments: pass parameters like id or first .
  • Aliases: rename fields to avoid conflicts.
  • Fragments: reuse field selections across queries.

Mutations

Mutations modify server-side data. They are the GraphQL equivalent of POST, PUT, and DELETE in REST. 

mutation CreatePost($input: PostInput!) {
  createPost(input: $input) {
    id
    title
    author {
      name
    }
  }
} # Variables { "input": { "title": "GraphQL for Beginners", "content": "GraphQL is a query language..." } }

Chapter 6

Resolvers

Resolvers are functions that return the data for each field in your schema. They connect GraphQL types to databases, APIs, or any data source. 

const resolvers = {
  Query: {
    users: () => db.users,
    user: (_, { id }) => db.users.find((u) => u.id === id),
  },
  User: { posts: (user) => db.posts.filter((p) => p.authorId === user.id) },
  Mutation: {
    createPost: (_, { title, content, authorId }) => {
      const post = {
        id: String(db.posts.length + 1),
        title,
        content,
        authorId,
      };
      db.posts.push(post);
      return post;
    },
  },
};

Resolver signature

Every resolver receives up to four arguments:

  • parent — the result of the parent resolver.
  • args — arguments passed to the field.
  • context — shared data like authentication.
  • info — query execution metadata.

Chapter 7

Type System

GraphQL is strongly typed. Every field has a type, and the schema validates queries before executing them. 

type User {
  id: ID!
  name: String!
  email: String
  age: Int
  posts: [Post!]!
}
type Post {
  id: ID!
  title: String!
  content: String
  published: Boolean!
  author: User!
}
type Query {
  users: [User!]!
  user(id: ID!): User
}
input PostInput {
  title: String!
  content: String
  authorId: ID!
}
type Mutation {
  createPost(input: PostInput!): Post!
}

Common scalar types

  • String , Int , Float , Boolean , ID
  • ! means non-nullable.
  • [Type] means a list of Type.
  • Custom object types and input types define your domain.

Chapter 8

Apollo Server

Apollo Server is the most popular GraphQL server for Node.js. It supports plugins, caching, error formatting, and federation. 

npm install @apollo/server graphql
const { ApolloServer } = require("@apollo/server");
const { startStandaloneServer } = require("@apollo/server/standalone");
const typeDefs = ` type Query { books: [Book] } type Book { title: String author: String } `;
const resolvers = {
  Query: {
    books: () => [
      { title: "The Awakening", author: "Kate Chopin" },
      { title: "City of Glass", author: "Paul Auster" },
    ],
  },
};
const server = new ApolloServer({ typeDefs, resolvers });
startStandaloneServer(server, { listen: { port: 4000 } }).then(({ url }) =>
  console.log(`Server ready at ${url}`),
);

Chapter 10

Authentication

GraphQL itself does not handle authentication, but the context object makes it easy to attach user identity to every resolver. 

const server = new ApolloServer({ typeDefs, resolvers });
const { url } = await startStandaloneServer(server, {
  listen: { port: 4000 },
  context: async ({ req }) => {
    const token = req.headers.authorization || "";
    const user = await getUserFromToken(token);
    return { user };
  },
}); // In resolvers const resolvers = { Query: { me: (_, __, { user }) => { if (!user) throw new Error("Not authenticated"); return user; }, }, };

Chapter 11

Pagination & Performance

GraphQL supports common pagination patterns like offset-based and cursor-based pagination. Cursor pagination is preferred for large or frequently changing lists. 

query {
  posts(first: 10, after: "cursor-123") {
    edges {
      node {
        id
        title
      }
      cursor
    }
    pageInfo {
      hasNextPage
      endCursor
    }
  }
}

Performance tips

  • Use DataLoader to batch and deduplicate database queries.
  • Persist complex queries with persisted queries.
  • Add query cost analysis to prevent abuse.
  • Cache frequently accessed fields at the resolver level.

Chapter 12

Capstone: Blog API

Build a complete GraphQL blog API with Apollo Server. The project consolidates schemas, resolvers, authentication, pagination, and performance optimization into one working API.

1. What is this project?

This is a fully functional blog backend. Authors can create posts, readers can add comments, and clients can query a paginated feed with nested relationships. It is a realistic example of a modern GraphQL service.

2. What it covers?

  • A strongly typed schema for users, posts, and comments.
  • Resolvers that fetch nested data from an in-memory store.
  • Authentication via context so only logged-in authors can create posts.
  • Cursor-based pagination for the post feed.
  • Apollo Server setup with GraphiQL / Apollo Sandbox.

3. How it is done?

The schema defines the domain, and resolvers connect each field to data. Context carries the authenticated user, and connection arguments drive pagination. 

type User {
  id: ID!
  name: String!
  email: String!
  posts: [Post!]!
}
type Post {
  id: ID!
  title: String!
  content: String!
  author: User!
  comments: [Comment!]!
}
type Comment {
  id: ID!
  text: String!
  author: User!
  post: Post!
}
type PostEdge {
  node: Post!
  cursor: String!
}
type PostConnection {
  edges: [PostEdge!]!
  pageInfo: PageInfo!
}
type PageInfo {
  hasNextPage: Boolean!
  endCursor: String
}
type Query {
  posts(first: Int, after: String): PostConnection!
  post(id: ID!): Post
}
type Mutation {
  createPost(title: String!, content: String!): Post!
  addComment(postId: ID!, text: String!): Comment!
}

Apollo Server serves the schema. The example below keeps data in memory; in production you would replace the store with a real database. 

const { ApolloServer } = require("@apollo/server");
const { startStandaloneServer } = require("@apollo/server/standalone");
const typeDefs = ` type Query { posts: [Post] } type Post { id: ID title: String author: User } type User { id: ID name: String } `;
const db = {
  posts: [
    { id: "1", title: "GraphQL Basics", authorId: "1" },
    { id: "2", title: "Apollo Server Tips", authorId: "2" },
  ],
  users: [
    { id: "1", name: "Ada Lovelace" },
    { id: "2", name: "Grace Hopper" },
  ],
};
const resolvers = {
  Query: { posts: () => db.posts },
  Post: { author: (post) => db.users.find((u) => u.id === post.authorId) },
};
const server = new ApolloServer({ typeDefs, resolvers });
startStandaloneServer(server, { listen: { port: 4000 } }).then(({ url }) =>
  console.log(`Server ready at ${url}`),
);

Run the server and test the API. 

npm install 
npm start 
# Test in Apollo Sandbox or with 
curl 
curl -X POST http://localhost:4000 \
-H "Content-Type: application/json" \
-d '{"query": "query { users { id name } }"}'

4. What did we learn from this capstone project?

  • A schema is a contract: it documents the API and validates client queries.
  • Resolvers separate data fetching from schema definition, making it easy to swap data sources.
  • Context is the cleanest place to attach authentication to every resolver.
  • Cursor pagination is more robust than offset pagination for frequently updated feeds.

5. How can I enhance this project in the future?

  • Persist users, posts, and comments in PostgreSQL or MongoDB.
  • Add subscriptions so clients receive new comments in real time.
  • Use DataLoader to batch related queries and avoid the N+1 problem.
  • Add search and filtering by title, author, or date range.
  • Write integration tests for queries, mutations, and error cases.
