Chapter 2

What is DevOps?

DevOps is a set of practices, tools, and a cultural philosophy that shortens the development lifecycle and provides continuous delivery with high software quality.

The DevOps feedback loop

Core principles

  • Collaboration: Break down silos between developers and operations.
  • Automation: Automate builds, tests, deployments, and infrastructure.
  • Feedback: Monitor production and feed insights back to development.
  • Continuous improvement: Iterate on processes and tooling.

Chapter 3

CI/CD Pipeline

A CI/CD pipeline automates the steps from code commit to production deployment. Each stage must pass before the next one begins.

Pipeline stages

1

Continuous Integration (CI)

Build, lint, and run automated tests on every commit.

2

Continuous Delivery (CD)

Package the application and make it ready for release.

3

Continuous Deployment (CD)

Automatically deploy every passing release to production.

Pipeline example

Push to main → Run tests → Build Docker image → Push to registry → Deploy to staging → Deploy to production.

Chapter 4

Git Workflow

A clean Git workflow is the foundation of CI/CD. Feature branches, pull requests, and protected main branches keep production stable. 

# Start a new feature
git checkout -b feature/add-auth
# Make changes and commit
git add .
git commit -m "feat: add JWT authentication"
# Push to remote
git push -u origin feature/add-auth
# Open a pull request, get review, then merge
# CI runs automatically on the PR

Recommended branch rules

  • main is always deployable.
  • Require pull request reviews before merging.
  • Require CI checks to pass before merge.
  • Delete feature branches after merge.
  • Use semantic commit messages.

Chapter 5

GitHub Actions

GitHub Actions is a CI/CD platform built into GitHub. Workflows are YAML files stored in .github/workflows . 

# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
      - name: Install dependencies
        run: npm ci
      - name: Run linter
        run: npm run lint
      - name: Run tests
        run: npm test
      - name: Build project
        run: npm run build

Key concepts

  • Workflow: A full automation process triggered by events.
  • Job: A set of steps that run on the same runner.
  • Step: A single command or reusable action.
  • Runner: The machine that executes jobs (e.g. Ubuntu, Windows, macOS).

Automated Testing

Tests are the safety net of CI/CD. If tests fail, the pipeline stops and the code is not deployed. 

{

    "test": "jest",

}
# Add to CI job
- name: Run tests with coverage
  run: npm run test:ci
- name: Upload coverage report
  uses: codecov/codecov-action@v4
  with:

Chapter 7

Docker in CI/CD

Docker ensures the application runs the same way in CI, staging, and production. CI pipelines commonly build and push images to a container registry. 

# Dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
EXPOSE 3000
CMD ["node", "app.js"]
# .github/workflows/docker.yml
name: Docker Build
on:
  push:
    branches: [main]
jobs:
  docker:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ secrets.DOCKER_USERNAME }}/myapp:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

Chapter 8

Environments & Secrets

Different stages need different configurations. Secrets store sensitive values like API keys and database URLs outside of source code. 

# GitHub Actions environment example
jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy to staging
        run: ./deploy.sh staging
        env:
          DATABASE_URL: ${{ secrets.STAGING_DATABASE_URL }}
          API_KEY: ${{ secrets.API_KEY }}
  deploy-production:
    runs-on: ubuntu-latest
    needs: deploy-staging
    environment: production
    steps:
      - name: Deploy to production
        run: ./deploy.sh production
        env:
          DATABASE_URL: ${{ secrets.PRODUCTION_DATABASE_URL }}
          API_KEY: ${{ secrets.API_KEY }}

Common environments

  • Development: Local coding and quick experiments.
  • Staging: Pre-production validation.
  • Production: Live user-facing environment.
  • QA: Dedicated testing environment.

Chapter 9

Deployment Strategies

There are many ways to release new versions. Choose a strategy based on risk tolerance, traffic size, and rollback needs.

Strategy comparison

Strategy How it works Best for
Rolling Replace instances gradually. Low-risk, zero-downtime updates.
Blue/Green Run old and new versions side by side, then switch traffic. Instant cutover and easy rollback.
Canary Release to a small subset of users first. High-risk changes and gradual validation.
Recreate Stop old version, start new version. Simple apps that tolerate brief downtime.

Chapter 10

Monitoring & Rollbacks

Deployment is not the end. You need to observe application health and be ready to roll back when something breaks. 

# Health check endpoint example
# GET /health
# Response: { "status": "ok", "timestamp": "2026-10-03T12:00:00Z" }

Monitoring checklist

  • Logs: Aggregate logs with tools like Datadog, Splunk, or Grafana Loki.
  • Metrics: Track CPU, memory, request latency, and error rates.
  • Alerts: Notify the team when thresholds are breached.
  • Rollbacks: Keep previous release artifacts so you can revert quickly. 
# Rollback to previous Docker image
docker pull myuser/myapp:previous-tag
docker stop myapp
docker run -d --name myapp -p 3000:3000 myuser/myapp:previous-tag
# Or via Kubernetes
kubectl rollout undo deployment/myapp

Chapter 11

Infrastructure as Code

Infrastructure as Code (IaC) lets you provision and manage servers, networks, and services through configuration files rather than manual clicks. 

# docker-compose.yml — simple IaC for local stacks
version: "3.8"
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
      - DATABASE_URL=postgres://db:5432/app
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app

Popular IaC tools

  • Terraform: Multi-cloud resource provisioning.
  • AWS CloudFormation / Azure Bicep: Native cloud templates.
  • Ansible: Server configuration management.
  • Pulumi: IaC using familiar programming languages.
  • Docker Compose: Lightweight local and single-host orchestration.

Chapter 12

Capstone: Node.js CI/CD

Set up a complete CI/CD pipeline for a Node.js API. The pipeline runs tests, builds a Docker image, pushes it to Docker Hub, and deploys to a remote server.

Requirements

  • Node.js API with tests.
  • Dockerfile that builds a production image.
  • GitHub Actions workflow that triggers on push to main.
  • Image tagged with the commit SHA.
  • Remote deployment via SSH using secrets.
  • Health check endpoint for monitoring.

Project files 

my-api/
├── .github/
│   └── workflows/
│       └── cd.yml
├── src/
│   ├── app.js
│   └── app.test.js
├── Dockerfile
├── package.json
└── package-lock.json

Dockerfile 

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
EXPOSE 3000
HEALTHCHECK CMD curl -f http://localhost:3000/health || exit 1
CMD ["node", "src/app.js"]

Full CD workflow 

# .github/workflows/cd.yml
name: CD
on:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
      - run: npm ci
      - run: npm test
  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}
      - uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ secrets.DOCKER_USERNAME }}/my-api:${{ github.sha }}
  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy to server
        uses: appleboy/ssh-action@v1.0.0
        with:
          host: ${{ secrets.SSH_HOST }}
          username: ${{ secrets.SSH_USER }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            docker pull ${{ secrets.DOCKER_USERNAME }}/my-api:${{ github.sha }}
            docker stop my-api || true
            docker rm my-api || true
            docker run -d --name my-api \
              -p 3000:3000 \
              --restart unless-stopped \
              -e NODE_ENV=production \
              -e DATABASE_URL=${{ secrets.DATABASE_URL }} \
              ${{ secrets.DOCKER_USERNAME }}/my-api:${{ github.sha }}

Required GitHub secrets 

DOCKER_USERNAME
DOCKER_PASSWORD
SSH_HOST
SSH_USER
SSH_PRIVATE_KEY
DATABASE_URL

Run the capstone locally 

# 1. Install dependencies and run tests
npm install
npm test
# 2. Build the Docker image
DOCKER_USERNAME=myuser
docker build -t $DOCKER_USERNAME/my-api:latest .
# 3. Run locally
docker run -d -p 3000:3000 --name my-api $DOCKER_USERNAME/my-api:latest
# 4. Verify the deployment
curl http://localhost:3000/health
# 5. Simulate rollback
docker pull $DOCKER_USERNAME/my-api:previous
docker stop my-api
docker run -d -p 3000:3000 --name my-api $DOCKER_USERNAME/my-api:previous

Checkpoint

Create the GitHub Actions workflow, add the required secrets, push to main, and confirm that the API is deployed and responding to the health check.
